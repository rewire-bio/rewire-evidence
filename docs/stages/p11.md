# P11: span resolution

Status: done for the 871 objects a public release mirrors, with every other result held to a recording made over all 1,167. Measured on 2026-11-23 against `rewire-benchmark-data` at `91f76cf8e61cba9d6037a01a19c9aa3051184900`.

With this stage `rewire-evidence spans measure`, `retag`, `control`, `value-check` and `show` are `npm run spans --` of the same names, and `rewire-evidence layers coverage`, `surface` and `show` are the three commands of `npm run layers --` that P10 left. A stored locator is resolved to a span in a layer by this library: both published ranges, the text, and the context that finds it again.

### What a line holds

For each result: the layers it could be tried on and how many were tried, whether it resolved, the resolver or the refusal reason, the layer, the character range and the byte range of the span, how many places the resolver chose between, the route to a table grid, the four readings of the stored value, and one digest over the span's text, its context, the row label and column heading it was crossed against, and the detail of a refusal. A line of `measure-store-spans.ts` holds seven of those members and the span's text.

The text of a layer of a restricted object is not public, so the committed lines hold none. `scripts/expected/store-spans.jsonl.gz` is the full recording with every text as 16 hexadecimal digits of a digest, 1.6 MB. The file `measure-store-spans.ts` itself writes is held by its SHA-256 for each view and is not committed.

### The eleven files

Both arms of the quote rule are measured, because the figures file holds both. The files are: the line for each result, the lines the legacy arm decides otherwise (101 over every object, 90 over the public ones), the lines of `measure-store-spans.ts`, the five tables, `span-resolution-figures.json`, the records file beside it, and what the command prints with the clock held still.

### How the two views are joined

A result is tried on the text layers of its sources that the sanity gate did not fail, and each layer is derived from one object. Where every one of those objects is held, the measurement reads nothing that is missing, so it is the measurement a cache of every object gives. 41,153 results are of that kind over the public objects and 11,125 are not. The recorder counts them in JavaScript and the gate counts them again in Python, and the two counts have to agree. The rule was checked against the two recordings before it was used: all 41,153 lines are the same in both, and none of the other 11,125 is.

So in CI the gate does three things.

1. It requires all eleven files to be what the TypeScript writes in the same job over the same objects, and to have the digests `scripts/expected/store-spans.json` states for the public view.
2. It requires each of the 41,153 lines to be the line the full recording has.
3. It builds the five tables and the figures from the 41,153 measured lines and the 11,125 recorded ones together, and requires the committed tables byte for byte and every committed figure.

The four figures that count layers read (`layers_read`, `layers_astral`, `astral_points`, `grids_read`) are in no result's line. In CI they are taken from the full recording, which states 436, 32, 3,248 and 167.

### The figures file does not regenerate whole at the pinned commit

`span-resolution-figures.json` names each input it was measured over by digest. It was written on 2026-11-19 when `data/entities/sources.jsonl` had 1,491 lines, and the pinned commit has 1,497. A run at the pin writes the same 173 figures, another digest and line count for that one input, and six more lines in the records file. The gate requires the figures, requires the file the TypeScript writes at the pin by digest, and requires that no record the committed file was measured over is gone or changed, which is the check `tests/omics-report-drift.test.ts` makes.

## Text is held as JavaScript holds it

A span is published in characters and bytes. Everything in JavaScript that finds text counts UTF-16 units, and the resolvers are written in those: a column is found by where its heading stands on a line, a sentence is given 900 units to end in, a quote needs four of them. A character beyond U+FFFF is two units, and 32 of the 436 layers the measurement reads hold one.

So `offsets.py` holds a layer one item of the string to a unit, which a Python string can do because it can hold half a surrogate pair. Every offset inside a resolver is then the TypeScript's own, and a span is converted when it is made. A layer with no such character is the same string either way, with no copy. A parse is put into the same form on its way in, and text is put back into characters on its way out.

## Patterns

The resolvers' fixed patterns are Python's own, written with JavaScript's classes: `\s` is `js.SPACE_CLASS`, a digit is `[0-9]`, `$` is the end of the text, and the `i` flag is `IGNORECASE` with `ASCII`. That last is JavaScript's rule only if nothing but its other case matches an ASCII letter, and a test holds it against Node's recording for all 128.

Three patterns the TypeScript runs with the `u` flag go through `jsregex` as before, from sets recorded from Node.

A caption pattern is built from the locator at run time, under the `i` flag: `Table S3` has to find `TABLE s3`. `jsregex` needs a recorded set for each letter, and the letters arrive with the locator. `scripts/fixtures/record_case_units.mjs` records the answer for every one of the 65,536 units, by matching, not from a case mapping: 2,313 match more than themselves. `jsregex.recorded_or_unit` reads it, and a pattern built at run time is translated with it. Where both recordings hold a letter they agree, and a test holds that.

## Where JavaScript is the specification

`tests/fixtures/spans.json` is recorded from the TypeScript by `scripts/fixtures/record_spans_fixture.mjs` in the `fixtures` job, on cases from `spans_cases.mjs`: 1,195 calls of 65 kinds, seven small trees for the figures file with 35 steps, and seven trees for the commands with 74 runs. Every one is replayed. No case needs pdftotext: a resolver is given text and the name of the normaliser that would have written it.

- **A span never holds half a character.** An end that falls between the two units of one is moved outwards. Recorded on text with characters beyond U+FFFF and with halves that have no partner, which Node counts as one character of three bytes.
- **The context is 48 characters cut from 96 units.** Recorded on a layer where the two differ.
- **A number is a double.** `Number(value)` of a line, a paragraph or a page gives NaN, an infinity or a fraction for text the grammar would not give, and each resolver does something of its own with it. `resolveDelimitedCell` throws a TypeError for a line that is no integer, and the port raises one. The others refuse, in words that print the number as JavaScript prints it.
- **`toFixed(1)` and `toPrecision(17)`** are written by `js.fixed` and `js.precision`, and `10 ** -n` is the nearest double for each n from 0 to 100, which is not the reciprocal of ten to the n. All three are recorded.
- **`normaliseLabel` lowers case as Node does**, a capital sigma and a dotted capital I included, and a letter beyond U+FFFF, which is two units while it is lowered.
- **The JSON reader takes a number from 48 units** and no more, and reads `\u` with `parseInt`, so `\u12G4` is U+0012, `\u-1ab` is U+FE55 and `\uzzzz` is U+0000.
- **A sheet's name is matched exactly and then whatever its case**, and two sheets that differ only in case give nothing.
- **A grid's offsets are checked against the layer.** Recorded with grids that say they are over a layer and are not.

The store recorder is also run over one of the command trees, with every object and with two taken out. The tests run the gate against those two recordings as CI runs it against the real ones, and then with one thing wrong in each: a digest, a file of the run, a recorded line, a count, a committed table, a committed figure, a record that is gone, another pdftotext.

## A comparison on generated input

`scripts/fixtures/compare_spans.mjs` and `compare_spans.py` run the TypeScript and the port on input put together at random and print where they part. It is not a gate and CI does not run it. Run once for this stage, on Node 24.22.3 with seed 20261123: 3,000 generated locators resolved under both quote rules against eleven of the recorded layers, and 6,000 texts made of the characters the two languages count, match and change the case of differently, given to 25 kinds of call, alone and as a layer. 228,000 calls, and none differed.

## Property tests

- Text in units counts as JavaScript counts and comes back whole, and the index of a layer ends on its three sizes.
- A span holds the text both of its ranges name, never half a character, and `reanchor` finds it unchanged where it is.
- A character offset and a unit offset are each other's inverse where a character starts.
- A label normalised twice is the label normalised once.
- An escaped cell is read back as it was, and every cell of a sheet block is found by its row and column.
- The JSON reader keeps every value of any document and where it is, and reads no document that is cut short or followed by more.
- A decimal is rounded half away from zero on its digits, and a number spelled without an exponent is the same number.
- A figures file written and read is the same file, and one that only gained records has not drifted.
- A document retagged once has nothing left to retag, where each tagged number is the first on its line.

## Where the port differs

Each of these is a place the TypeScript cannot be recorded, or does something a machine decides.

- **A JSON document nested some thousands deep.** The TypeScript's reader calls itself for each level, overflows Node's stack at a depth that is the machine's, catches that, and reports the layer as not JSON. This reader keeps its own stack and reads the document.
- **A grid layer whose lines are JSON and not a grid.** The TypeScript reads each line with `JSON.parse` and trusts its shape. The port holds each line to the shape and counts the grid as unreadable. No registered layer is one, because a grid's bytes are named by their hash.
- **A layer that cannot be derived again for a reason other than its hash.** The detail of the refusal is Node's error text there and this library's here. Neither view of the store reaches it.
- **`spans control` reads the value-check files in the order of their folders' names.** Node reads them in the order the directory lists them.

Four branches of the TypeScript cannot be reached and are not in the port, each with a comment where it would be: going on from a refused keyed row to a cell or a line address, which was resolved above; a decimal point among the digits of a number written with an exponent; a heading row outside its block; and the two sums `coverageOf` checks its own rows against.

## TypeScript behaviour noted, not changed

- **A measurement loses a PDF layer without a word when pdftotext fails on it.** `layerOf` catches the failure, the layer has no text that time, and every result on it is refused as `layer_not_readable`, or keeps a refusal that got further and shows nothing at all. Issue #272 of the data repository lists this as open. It happened in the first CI run of this branch: the TypeScript read one PDF of 22 pages in the first pass of the command, and failed on it in a later pass and again in the pass that writes the lines, so 144 results lost their spans and `layers_read` fell by one. This library read the same PDF every time in the same job, and 150 conversions of it on this machine gave one text. What pdftotext said was not kept, so the cause is not known. The second run had no failure. The recorder now asks pdftotext again when it fails, up to three times, writes each failure to `pdftotext.json`, and ends the recording when a PDF still has no text or gives two texts. The job prints that file.

- **`spans measure` ends on a blank line in a results file or in `sources.jsonl`.** `readResults` and `sourceIds` pass over a blank line. `inputFiles` then names each line of the same file as a record and calls `JSON.parse` on the blank one, and the command leaves with a stack trace and writes nothing. Recorded on a tree with one such line. The port refuses in a line with status 1.
- **`retag` rewrites the wrong number where the same number stands earlier on the line.** It looks for the printed number from the start of the tag's line and takes the first place it is printed there. Two tags on one line that print the same number are both rewritten at the first, and the second number is left: `3 <!-- figure:three -->3 <!-- figure:three -->` with a value of 30 becomes `3030 <!-- figure:three -->3 <!-- figure:three -->`. Recorded, and the port does the same.
- **`retag` looks on the tag's line for a number printed on the line above it**, for the same reason. It rewrites that number where the tag's line prints it somewhere else, and nothing where it does not. Recorded.
- **The inputs of the figures file include test files.** `inputFiles` takes every `.ts` file directly in each folder, so a change to `grid.test.ts` or `layers.test.ts` reads as drift of the figures.
- **`layers show` prints the list of layers and then throws** where the first layer cannot be derived again. The port prints the list and the reason and exits 1.
- **`spans control` lets the last value-check file decide** where two files name one result with two statuses, and which file is last is the order the directory lists them.
- The committed figures file is stale in one input, as above.

## Known gaps

- 11,125 of the 52,278 results are not measured in CI. They are held to a recording made on one machine, and nothing in CI can say that recording is what the TypeScript writes for them. The 41,153 that CI does measure have to agree with it line for line.
- `spans control`, `spans value-check`, `spans show` and `layers show` are held on small trees and are not run against the pinned store in CI. `layers coverage` and `layers surface`, which read no object, are held to what the TypeScript prints for the pinned store.
- The legacy arm is held by the lines it decides otherwise and not by a second full file.
- The `layers` job is longer by about 13 minutes, 18 in all: 6 to 8 for the TypeScript's measurement, which is five passes, and 6 to 7 for this library's, which is two.
- A pdftotext that fails once under this library fails the gate, here and in P10. Running the job again is the remedy, and the recorder's own failures are written down so that the two can be told apart.

## Running it

```sh
python scripts/fetch_public_objects.py <checkout> objects
python scripts/verify_store_spans.py <checkout> objects
```

It needs `pdftotext version 26.08.0` on the path, built as `scripts/build_poppler.sh` builds it. To record the TypeScript beside it, in a checkout of the data repository at the pinned commit with its dependencies installed:

```sh
ARCHIVE_CACHE=<objects> node_modules/.bin/tsx <rewire-evidence>/scripts/fixtures/record_spans_store.mjs <folder> 2026-11-19
python scripts/verify_store_spans.py <checkout> <objects> --recorded <folder>
```

`scripts/fixtures/assemble_spans_expectation.py <full> <public>` writes the committed expectation from a recording over every object and one over the public ones. Moving `STORE_REF` means making both again, on a machine that holds every object, on the Node the `fixtures` job names.
