## The registry is generated

The 700 lines of `attribute-registry.ts` were not copied. `scripts/fixtures/record_validation_fixture.mjs` imports `attributeRegistry` in the `fixtures` job and writes it to `src/rewire_evidence/data/attribute-registry.json` with the commit it was read at and the SHA-256 of `JSON.stringify(attributeRegistry)`. A test recomputes the digest from the members as Python holds them. CI fails if the file is not what the TypeScript produces, and refuses to run a gate unless the registry, the two expectation files, the layout pin, `STORE_REF` and the checkout all name one commit.

## The rule identifier

There are three kinds of refusal, and each has its own identifier.

- A plain `Error`. The message is the only identifier there is, and it is compared whole. `RecordError` carries it.
- zod's issues, where a validator calls `.parse`. Each issue is a code, a path and a message, and all three are compared for every issue, in zod's order. `SchemaError` carries them. `attributeIssues` prints only the first issue's message, so which issue comes first is part of what is compared.
- A JavaScript `TypeError`. The TypeScript reports no fault of the records in these cases. It fails, in V8's words, because a value was not the shape it assumed. Python raises `JsTypeError` in the same places, and the comparison is on that alone. The words are not reproduced.

## What the validators do that is easy to miss

All recorded, none read from documentation.

- `validateRecords` takes the records in the order given and applies every rule to one record before it looks at the next, so with two faulty records the first by ID is reported, and within a record the first rule. `loadRecords` runs attributes, derivations, descriptions and concerns over the records as they are filed, and `validateRecords` over the records by ID.
- A check added to a zod object with `superRefine` runs only if no member is of the wrong type. A member that failed its own check, or an unrecognised key, does not stop it. So a review with a misspelt date still gets the rule about the retired review method, compared as text.
- A length check runs on any value that has a `length`. A list given where text was wanted is reported for its type and may be reported for its length too.
- zod's `.url()` trims the text and then asks JavaScript's URL parser, which accepts any scheme. `mailto:a@b`, `c:/x` and ` https://example.org ` are all URLs to it. The source rule of `validateRecords` then requires `http:` or `https:`.
- The catalogue query reads every record through `normalizeRecords` and `normalizeAttributes` before it resolves a panel. A source with `license` and `licence` holding different values is refused by `validateRecords` only if some record has panels.
- An excluded record is not in the query. Its own panels are never looked at, and a panel naming it finds nothing.
- An assessment record shows the panels of the records below it. Below means `part_of` links, or one `evaluates_task` link from the record itself, each backed by a checked claim. A panel is not shown on a task two `evaluates_task` links away. The corpus holds both sides of that.
- A result with no `numeric_value` at all is refused. Only an explicit null means there is no number.

## Where Python is stricter, or different

- `load_records` wraps a line the schema refuses in `StoreError`, naming the file and line, with zod's issues on its cause. The TypeScript throws the `ZodError` bare. This is unchanged from P2.
- A source URL, or an attribute of type `url`, whose host has a character outside ASCII or a label starting `xn--` raises `weburl.UndecidedHost`. JavaScript judges such a host with Unicode's IDNA mapping, which is not ported. No URL in the store has such a host, and nine recorded inputs hold the port to refusing to answer.
- `JsTypeError` stands for every JavaScript `TypeError`. A source with no URL is one: the TypeScript's `new URL("undefined")` throws `Invalid URL` and never names the record.
- `panels.py` leaves out two things the query does that no validated record can reach. It does not follow identity links between models, because no assessment record may hold one, and it does not repeat the numeric value rule, because `validateRecords` has already applied it to the result itself. `resolve_panels` on records that have not passed the earlier rules is therefore not what the query would do, and its docstring says so.
- The validation gate reports a store a validator refuses as one problem and exit 1. It stops at the first refusal, as `loadRecords` does, and does not go on to measure.
- `normalize_attributes` works on rows whose keys are in the order JavaScript lists them, as `js_value` and `Record.row` give them.

## Known gaps

- The corpus is not a proof. `zod.py` is the constructs these schemas use and no more: text, numbers, booleans, literals, lists, fixed-length lists, strict objects, records, unions, optional and nullable members, and the checks named in it. Two of zod's rules are in the port and reached by no schema of the validators, and are tested as zod's rules and not as recordings: a required member that accepts anything, and a union with one option that got as far as its checks. The tests require the fixture to name zod 4.6.5.
- Per-rule coverage is on the 228-record base store. On the whole store 19 faults are seeded, one for each family of rule, because each runs a validator over 93,216 records.
- JavaScript's `TypeError` messages are not reproduced.
- Hosts that need IDNA mapping are not judged.
- `toLowerCase` and Python's `lower` follow the Unicode version each runtime ships. Thirteen recorded inputs agree, including dotted capital I and final sigma. A character whose case mapping changed between the two versions would compare differently in a shared-description check.
- The query sorts IDs with `localeCompare`, which depends on the locale Node runs in. For IDs of lowercase letters, digits and hyphens in an English locale it is the order of UTF-16 units, which nine recorded lists hold. The port sorts by unit.
- The text output of `records descriptions` for a store that has problems is ported from reading the TypeScript. Only the empty result on the pinned store was recorded.
- A member named `__proto__` directly inside `attributes` is dropped by the record schema before any validator sees it. Inside a row that never went through the schema, `normalize_attributes` treats it as any other name, and the TypeScript may not.
- The gaps of the earlier stages still stand: a number beyond every double, and a value nested deeper than Python will recurse.
- The fixture is 3.4 MB, most of it the damaged schema values and the base store.
- The write path is P6. `add` and `change` are not ported, and neither is the SHACL step.

## A departure from the port plan

The inventory recommended leaving comparison panels to the TypeScript CI, on the estimate that validating them needs the 1,033-line query engine. Resolving a panel needs about 250 lines of it: the claim index, the roll-up of an assessment record to those above it, and `resolveComparisons`. That is ported, so `records check` in Python checks what the TypeScript checks, and the 716 owners and 1,178 panels of the store are held to the query's own answer by digest. Result rows, listing, paging, readiness and the evidence table are not ported and are not needed.

## Needs the owner

- Unchanged from P2 and P3: `main` has no branch protection and the repository has no rulesets, so nothing requires the `checks` and `fixtures` jobs before a merge. That is a repository setting, which this workstream does not change.

## Found in the TypeScript, not changed

- `attributeIssues` looks a key up on the registry's plain object, so an attribute named `constructor`, `toString`, `valueOf`, `hasOwnProperty` or any other member every object has is taken as declared. If it is null the usual message about null is given. Otherwise `schemaFor` calls `startsWith` on a function and the check fails with `type.startsWith is not a function`. A batch holding such an attribute stops `records add` with a stack trace and no record named.
- The same lookup makes a `missing_metadata` reason for a field named `constructor` report `constructor has a value and a missing_metadata reason`, when the record has no such attribute, and never report it as undeclared.
- `normalizeAttributes` looks a free-text missing reason up the same way. The reason `toString` becomes an entry with no reason at all.
- `validateRunGuide`, `validateRunRecipes` and `resolveComparisons` test a source's artifact hash with `String(value)`. A hash given as a one-item list passes them. `validateAttributes` refuses it first when both run.
- `derivationIssues` joins the script path to the root with `path.join`, so a path starting with a slash is read below the root and passes, where the attribute schema requires a relative path. On a derivation of another shape it fails with a `TypeError`. Both are behind `validateAttributes` in `loadRecords`.
- `entries` in `concerns.ts` takes a list inside `evidence_concerns` as an entry. It has no `applies_to`, so it counts as a concern over the whole source and withholds every panel citing it.
- The query's claim index stringifies a claim's `field`, and `resolveComparisons` compares it strictly. A checked claim whose `field` is a one-item list backs a link for rolling results up and not for a panel's path to its owner.
- An owner whose `comparison_panels` is `0`, `""`, `false` or `null` is skipped by `validateRecords`. The same value on a record below another owner is refused as an invalid published comparison.
- A source with no URL, or one the URL parser refuses, fails `validateRecords` with a bare `TypeError: Invalid URL`. Other refusals name no record either: a literature audit, run documentation, a run guide or recipes on the wrong kind of record, a run guide naming another record, duplicate recipe IDs, an unknown recipe, a private field, and every refusal that is zod's issues.
- A URL with spaces around it passes both the `url` attribute type and the source rule, and is stored as written.
- `convertUncertainty` reads a level such as `"x%"` as not a number and writes `"level": null`.
- The description rules use `\b` and the `i` flag without the `u` flag, so they see ASCII letters only. `Identity as reported` with a dotless i is not caught.
- The earlier TypeScript findings in the P1 and P2 and P3 notes still stand.
