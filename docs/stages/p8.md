## Where JavaScript is the specification

The pack is small, and most of what could go wrong in a port of it is in what JavaScript does with text and numbers.

- **Patterns.** The 22 patterns of the pack and of `parseCell`, and the 20 of the table reader, run through `jsregex`, with their sets of characters recorded from Node, as the locator grammar's do. Under the `i` flag with no `u` flag a long s is not an `s` and a Kelvin sign is not a `k`, `\d` is an ASCII digit, and `\s` has U+FEFF and lacks U+0085. The recorded cases reach each of these. A group JavaScript numbers is given a name, because `jsregex` runs only named groups, and a group that is only tested is written as one that captures nothing. Tests hold the patterns to the TypeScript's own text with exactly those changes undone: the anchor, the column, the seven token patterns and `NOT_REPORTED` from the modules as they run, and every pattern of `tables.ts`, those `parseCell` writes inside its functions included, from the file as the compiler reads it.
- **A tag closed by whatever opened it.** The table reader has two patterns that end with a reference to their first group: a `script` or a `style` closed by the same word, a `td` or a `th` closed by the same. `jsregex` runs no reference to a group, so each is written as its two alternatives in turn. The recorded cases have a tag closed by the other one, in both orders and in mixed case.
- **The patterns of `tables.ts` are compared with its text.** The recorder reads every pattern out of the file with the TypeScript compiler, 32 of them, and a test holds each pattern of `cells` and `tables` to the one written there, with the names of groups and the two rewrites above undone.
- **A reference to a character.** `String.fromCodePoint` throws past U+10FFFF, `parseInt` gives the nearest double to a long number, and a number too long to be finite is `Infinity` in the message. Half a character written as a reference is half a character.
- **`matchAll`.** `columnOf` reads every column a locator names and keeps the last that is not a column group. `JsPattern.all` is JavaScript's loop, one character on after a match of nothing. Of 53 recorded runs of it, 49 agree and 4 are refused for the text they are run on, for the reason the P7 notes give.
- **`Math.round`** takes the larger of two whole numbers equally near. Python's `round` takes the even one, and `floor(x + 0.5)` is wrong for the largest double below one half.
- **`10 ** n` is not the nearest double for every n.** Node 24.22.3 gives `1.0000000000000001e+23` for 23 and is one step out again for 210. Node 26.7.0 gives the nearest double for both. So the powers are data: `src/rewire_evidence/data/powers-of-ten.json` holds the 309 finite ones as the recorded Node gives them, and a test names the two that differ.
- **Order.** `sort()` and `<` order text by UTF-16 unit, so a character beyond U+FFFF sorts before U+FF5A. The source IDs of a column, the subjects of C9, the statuses in its detail, the tie between two units in C1, the changed keys of C13 and the rises of the ratchet are all ordered that way, and each has a recorded case where the two orders part.
- **Lowercase** is JavaScript's, from the recording P7 made: a dotted capital I becomes two characters and a final sigma its own letter.
- **Objects list a name that is a whole number first.** The counts of a run are written in that order.
- **Half a character** in a record is written into a detail as an escape by `JSON.stringify` and into the report as U+FFFD by Node.

## Where the port differs, on purpose

- **A record with an ID that is not text is refused**, as are source IDs that are not a list. The TypeScript would write `undefined` into the report or fail on a type. The store reader refuses the first before any check runs.
- **C13 refuses a record whose kind is not text or whose links are not a list.** `normalizeAttributes` fails on a type for a result or an evaluation with no links and takes any other kind, and `normalize_attributes` is held to it only for records with both.
- **A baseline file is read strictly.** Counts that are not numbers and checks that are not objects are refused before anything is compared. The TypeScript takes whatever JSON the file holds. A count that is absent is refused as missing: the total, or a check's count of its findings. The TypeScript reads such a file and leaves that count out of the comparison, so the ratchet holds nothing on it. A recorded case has a baseline with neither, which the TypeScript compares on its one rule alone.
- **`--date` has to be written YYYY-MM-DD.** Anything else is a command line that cannot be read, and exits 2. The TypeScript joins whatever it is given into the name of the report, so `--date ../../escaped` writes `maintenance/reports/escaped.tsv` and an empty date writes `checks-.tsv`.
- **A root with no `data` folder is refused by name**, as the write commands refuse it. The TypeScript fails on the vocabulary it cannot find. A root with the two vocabularies and no store is still read as a store of no records, with no findings and status 0, because that is what the TypeScript does: two recorded cases hold it.
- **A checkout that cannot be read is refused in one line.** The TypeScript leaves with a stack trace and the same status, 1.
- **A command line that cannot be read exits 2.** The TypeScript prints its usage and exits 1. `--date` with nothing after it is a usage error here and today's date there.
- **`--root` and `--out` are added.** The TypeScript reads the working directory and always writes the report into it.
- **The time a run took is taken from an injected clock**, so a test can hold the line that states it.
- **A `colspan` above 1,000 is refused.** The TypeScript pads the row with that many empty cells, and for a number too long to be finite it never returns.
- **A pattern handed to `table_matching` or `layout_rows` may not have the `g` flag.** With it JavaScript's `test` starts where its last match ended, so the answer depends on the call before.
- **What the reader throws is one exception, `TableError`**, with the TypeScript's message. The TypeScript throws an `Error` or, for a reference past the last character, a `RangeError`.
- **One fallback of the TypeScript cannot be reached from JSON it reads.** C13 says `the attribute order` when a record would be rewritten with no key added, dropped or changed. JavaScript lists a name that is a whole number first, so no record it reads is in another order, and no recorded case has those words. A row made in Python in another order does, and a test holds that.

## Known gaps

- **Nothing in the port plan calls the table reader.** Its only callers in the data repository are the 16 benchmark extractors under `scripts/omics/extract/`, which the plan leaves in TypeScript, and one test file. The deterministic extraction of P12, `shared/omics/extract/`, imports `parseCell` from `tables.ts` and nothing else, and the grids of P10 are read by another file, `shared/archive/layers/grid/tables.ts`. So no later stage's oracle reaches this reader, and the recording made here is all that holds it.
- **The table gate reads what is committed, which is 97 files.** The extractors read artifacts from the object cache, which a clean checkout does not have. No committed file is a PDF text layer, so `layout_rows` is held by the 14 recorded cases alone, as are `table_matching` and `sectioned`, which need an argument only an extractor supplies.
- **C13 has no finding in either oracle**, because the store was migrated before the check existed. It is held by the 98 normalisation cases of P4, run through the check.
- **The baseline's `notes` are the TypeScript's sentences and carry the numbers of the first run.** `checks baseline` writes them whatever the run counts, as the TypeScript does.
- **The first-run oracle is one commit of the store and will not move.** A pin bump leaves `CHECKS_REF` where it is unless the data repository pins a new baseline, in which case `CHECKS_REF`, `CHECKS_ROWS` and `CHECKS_RECORDS` follow the baseline's `commit`.
- **The recorded lines are 0.49 MB in the repository**, in four files, and a pin bump replaces them.
- **The Node the data repository runs is not pinned there.** Its workflows say `node-version: 24` and its `package.json` says `>=22.13`, so the build that runs the TypeScript moves without a commit. The port holds what Node 24.22.3 does. A step in CI fails when the workflows of the pinned checkout name another major version, which is all that can be seen from here. A move inside a major version cannot be seen. What follows the build is `10 ** n` in `roundsTo`, for a value printed with 23 or 210 decimals, and the Unicode tables behind the patterns and the lowercase mapping. No stored value is printed with 23 decimals.
- **Three rules have no row in the store.** `metric-not-a-concept`, `numeric-not-a-number` and `would-be-rewritten` are held by the recorded small stores alone, and a test requires that those stores raise all sixteen rules.
- **The gates are still not required by the repository.** `main` has no ruleset, so a pull request can be merged while `checks`, `writes` or `fixtures` is red. That is a repository setting, which this workstream does not change.

## What a pin bump now takes

Bumping `STORE_REF` changes the pinned run. The `fixtures` job then fails, and its `schema-fixtures` artifact holds the new `store-checks.json` and the three files of lines to commit. `CHECKS_PINNED_ROWS` in `checks.yml` is pinned by hand. If the bump takes in a new committed baseline, `CHECKS_REF`, `CHECKS_ROWS` and `CHECKS_RECORDS` change with it, and a step fails until `CHECKS_REF` is the commit the baseline names.

The bump also changes what the table reader is held to if the commit adds, drops or changes an HTML or XML artifact, or changes `tables.ts`. The same artifact then holds the new `store-tables.json` and its lines, and `TABLE_ARTIFACTS`, `TABLES`, `TABLE_CELLS` and `TABLE_LINES` in `checks.yml` are pinned by hand. A changed pattern in `tables.ts` fails the test that holds the patterns to the file.

Moving the Node version means recording `powers-of-ten.json` again with everything else. Node 26.7.0 gives other powers for 23 and 210 than 24.22.3 does.

## Found in the TypeScript, not changed

`rewire-benchmark-data` was read and not touched.

- **A reference by name finds what every object has.** `decode` looks a name up in an object, so `&constructor;` is read as `function Object() { [native code] }`, and `&toString;`, `&valueOf;`, `&hasOwnProperty;`, `&isPrototypeOf;`, `&propertyIsEnumerable;` and `&toLocaleString;` likewise. The port writes the same seven.
- **A reference is read more than once.** The three kinds are three passes, so `&#38;lt;` is read as `<` where a browser reads `&lt;`.
- **A `colspan` is trusted.** `colspan="100000000"` pushes that many empty cells, and a number too long to be finite never ends the loop.
- **A label inside a cell is taken for the caption of its table.** `caption(body)` looks through the whole table, cells included, before it looks at what stands before the table.
- **One line of `tables` cannot be reached.** `if (from < previousEnd) continue` follows a search that starts at `previousEnd`.
- **`tableMatching` and `layoutRows` give another answer on a second call when the pattern has the `g` flag**, because `test` keeps its place.
- **A printed value so large that a hundred times it is infinite is classed `rescaled-by-100`, whatever the numeric value is.** `same(a, b)` is `Math.abs(a - b) <= Math.max(Math.abs(a), Math.abs(b)) * 1e-12`, and with `a` infinite both sides are infinite. A recorded case has `printed_value` `1e307` and `numeric_value` `5` reported as rescaled. No stored value is that large.
- **C13 takes the whole run down on a result or an evaluation with no `links`.** `normalizeAttributes` throws `Cannot read properties of undefined (reading 'find')`. The checks read the store without validating it, so the pack's own promise to report on what the store holds does not cover this record.
- **`roundsTo` depends on the Node it runs on for 23 and 210 decimal places**, through `10 ** places`, as above.
- **The baseline's `notes` are literals in `cli.ts`.** Re-pinning after a count changes writes the sentences of the first run into the new file unless they are rewritten first, which the second of them says.
- **A run above the baseline on one count and below it on another is reported as above only.** The line saying the baseline can be lowered is printed only when nothing rose.
- **`--date` with nothing after it writes today's report** and says nothing about the missing date.
- **`--date` is not checked.** It is joined into the path of the report, so a date holding `../` writes the report outside `maintenance/reports`.
- **A baseline with a count missing is compared without it.** `risesAboveBaseline` skips a key the baseline does not give, so a baseline file with no `total_findings`, or a check with no `findings`, lets that count rise unseen.
- **The workflows do not pin the Node build**, only its major version, and `roundsTo` gives another answer on another V8 for a value printed with 23 decimals.
- **The key of a concept is its IRI with the scheme's length cut from the front**, whatever the IRI starts with. A subject outside the scheme's namespace that is stated to be in the scheme gets a key that is the tail of some other IRI, or nothing.
