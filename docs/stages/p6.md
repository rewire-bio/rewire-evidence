# P6: the write path

Status: done. Measured on 2026-11-21 against the history of `rewire-benchmark-data` up to `91f76cf8e61cba9d6037a01a19c9aa3051184900`, and against its TypeScript at that commit with zod 4.6.5 and Node 24 in the `fixtures` job.

With this stage `rewire-evidence records add` and `rewire-evidence records change` are `npm run records -- add` and `-- change`, apart from the SHACL step, which still runs the data repository's own commands.

## What was ported

| TypeScript, in `scripts/omics/records.ts` | Python |
| --- | --- |
| `addBatch` | `writes.plan_add` |
| `recordChanges`, for records edited in place | `writes.plan_change` |
| `applyChanges` and the `ChangeLine` shape, for a changes file | `writes.plan_changes_file` |
| `writeStore`, as a list of whole files to write | `store.store_bodies`, held by a `writes.Plan` |
| `writeCheckedAgainstShapes`: write, check, and put every file back on failure | `writes.write`, with the check passed in |
| The two commands it runs for the check | `writes.shapes_check`, which runs the same two |
| `new Date().toISOString().slice(0, 10)` | `writes.today` |
| The `add` and `change` branches of the command line | `cli.py`, with `--root` and `--dry-run` added |

Deciding a write and making it are separate. The three `plan_` functions read the store and return every file `writeStore` would write, whole, and write nothing. `write` puts a plan on disk. That split is what makes `--dry-run` and the replay gate possible, and it changes nothing about the bytes: the TypeScript rewrites every store file that holds a row, and `write` writes the ones whose bytes differ, which leaves the same disk.

## What the TypeScript does, which the port keeps

These were read from the source and then recorded from it. Each has a case in the fixture.

- `addBatch` runs the validators in its own order, not `loadRecords`' order: vocabularies and attributes over the additions alone, then descriptions, derivations, concerns and `validateRecords` over the store followed by the additions, unsorted. Every line of the batch is parsed before any ID is compared, so a line that is not a record is reported before a duplicate on an earlier line, and a duplicate before a vocabulary fault.
- `recordChanges` validates nothing. It parses each line with the schema, takes the digest of each named record and adds an entry. A record no rule accepts is recorded as changed. An ID named twice gets two entries. A record that was not edited gets an entry and keeps its digest.
- `applyChanges` checks each line against the stored record and its provenance row and parses the new record with the schema. It runs no other validator either.
- Both forms of change build a `Map` of the records by ID. Of two lines with one ID the later is the record, silently.
- A record edited in place into another kind is written to the new kind's file. Its old file receives no row, so it is not rewritten and the old line stays.
- `writeStore` writes every record and provenance row from its parsed form. A line with its keys out of schema order, a provenance row written with spaces, blank lines and a missing final newline are all rewritten by any `add` or `change`, in files the command has nothing else to do with.
- A provenance row keeps the members it was read with, in JavaScript's order for them, so a member named `7` moves to the front. A change sets `sha256` where it stands and adds to the end of `changed_by`.
- The date is the UTC date.

## The oracle

There are three: the store's history, a write the TypeScript made on the pinned store in CI, and the TypeScript's answers on small stores. History has no example of one of the three commands, and holds only writes that were accepted.

### Merged pull requests, replayed

`scripts/verify_store_writes.py` reads a clone of the data repository that has its history. For each case in `scripts/expected/store-writes.json`:

1. the store is laid out in a scratch folder as the merge's first parent holds it, with `data/vocab`, `data/ontology/mapping.json` and `scripts/omics/derive` as the merge commit holds them, which is the checkout the command ran in;
2. the commands the pull request ran are run again by this library, adds first: `add` with the batch file the merge commit holds, then `change` with the IDs, the review, the batch folder and the date its provenance rows record;
3. every file under `data/entities`, `data/evidence` and `data/provenance` is hashed as git hashes a blob, and the names have to be the ones the merge commit's tree lists, file for file. That covers the files that changed and the ones that should not have.

The comparison needs none of the merge commit's store files, so a clone made with `--filter=blob:none --no-checkout` is enough, and the gate fetches the blobs of the parents' stores in one request per case. A mismatch is reported with the file, both blob names, and the line and byte where the two first differ.

### A changes file, applied to the pinned store by the TypeScript

No merged pull request has used `records change --changes`: the form arrived in the pinned commit itself. The data repository does hold an input for it, in `tests/agents-reviewer-fixtures/update/`: a batch of one source and a changes file that cites it from the model `discovery-model-spliceai`, based on that record's digest at the pinned commit.

So `scripts/fixtures/record_write_fixture.mjs`, in the `fixtures` job, copies the pinned store to a scratch folder, calls `addBatch` and then `applyChanges` on it with those two files, and writes the git blob name of every store file left to `scripts/expected/store-recorded-writes.json`. The write gate lays out the pinned commit's store from history, runs `add` and `change --changes` with the same files, and has to arrive at the same 79 names. Four files differ from the pinned store and 75 do not. The TypeScript's bytes are not kept, only their names, so a mismatch here is reported by file and not by line.

### The TypeScript, on small stores

`tests/fixtures/write-path.json` holds the refusals of all three commands, and most of what there is to know about a changes file.

`scripts/fixtures/record_write_fixture.mjs` runs in the `fixtures` job, inside the pinned checkout with its locked dependencies. It calls `addBatch`, `recordChanges` and `applyChanges` on 110 stores written to a scratch folder, with the clock stopped at `2026-02-04T04:30:00Z`, an instant that is still the day before in New York. For each it writes down what the call returned or how it refused, and every file it left different. The cases come from `scripts/fixtures/write_cases.mjs`, which builds them from the ten-record store already in `tests/fixtures/validation.json` and states for most of them whether the TypeScript should accept. The recorder fails if the TypeScript disagrees, so a case that does not test what its name says cannot be recorded quietly.

## Measured result

- Replay: 12 of 12 merged pull requests reproduce, and so does the write the TypeScript recorded on the pinned store. Together 2,601 records added and 1,218 changes recorded, 1,027 files compared byte for byte by blob name. CI pins all four numbers, requires every merge to be an ancestor of `STORE_REF`, and requires the recorded write to have been made at `STORE_REF`.
- Fixture: 107 of 110 recorded writes agree, in the files left and in the refusal. The other 3 are the one deliberate difference below.
- The commands are run on every fixture case with a stand-in for `npm`: once with `--dry-run`, which has to leave every file alone and run nothing, and once for real, which has to leave the files the TypeScript left and print the line it prints. A stand-in that fails, at either of the two commands, has to leave the store as it was, with no file the write created.
- On the pinned store CI dry-runs `records add` of a batch the store holds, which has to be refused by name, and `records change` of one record, which has to show one provenance row lost and one gained and leave the checkout clean.
- Coverage: 100% of lines and branches of `src/rewire_evidence`, with no line excluded.

Properties checked with Hypothesis:

- recording a change makes an edited store load again, changes only the provenance rows of the records named, and with nothing named writes nothing;
- a batch in any order adds the same files;
- a write that is refused, by an error or an interrupt, leaves every file as it was and no new file, and the check sees the store fully written;
- the lines a diff removes and adds take the old file to the new;
- the date does not depend on the time zone the moment is told in;
- a blob is named as `git hash-object` names it.

## Where the port differs, on purpose

- **A number beyond every double.** `JSON.parse` reads `1e400` as infinity and `JSON.stringify` writes it as `null`. The TypeScript's `add` and both forms of `change` therefore store `null` in place of the number, and for a record already in the store `records change` rewrites the number as `null` in passing. This library takes the digest as the TypeScript does, so it agrees on whether a line is stale or unchanged, and then refuses to write the line. Three recorded cases show the TypeScript storing the `null`.
- **`--root`.** The TypeScript writes the checkout it is run in. The commands here take `--root`, and the working directory by default.
- **`--dry-run`.** New. It prints a unified diff with no context of every store file the write would alter, blank lines and a missing final newline included, then one line saying what the write would do. It runs no shapes.
- **A refusal.** The TypeScript prints the error with a stack trace and then `The batch failed validation; the store is unchanged.` This prints the message in one line, with the batch line it came from where zod's words name none, and then the same sentence. Status 1 in both.
- **A command line that cannot be read** exits 2 from `argparse`, where the TypeScript prints its usage and exits 1. `records change` with neither IDs nor `--changes` is one.
- **A store that could not be put back.** If a file cannot be restored after a refused write, the TypeScript fails inside its own handler. This raises `RestoreError` naming the files, and the command does not say the store is unchanged.

## Known gaps

- **The SHACL step is not ported.** `shapes_check` runs `npm run -s kg -- subset` and `npm run -s kg:build -- --shapes-only` in `--root`, as the TypeScript does, so a real write needs a data repository checkout with its dependencies installed. It becomes in-process with P13. The replay gate does not run it: it writes nothing, so it cannot change a byte the gate compares. What is tested here is that the two commands are run with the TypeScript's arguments on the written store, and that a failure of either undoes the write.
- **`records change --changes` has no merged batch to replay.** Its oracle is one write the TypeScript made on the pinned store, of one record, and the 54 recorded cases on small stores.
- **A replayed `records change <id>...` takes its edit from the oracle.** The edit a person made before running the command is an input, so the replay copies each named record's line from the merge commit. What the case proves is the provenance rows and the rewrite of every file, not the edit.
- **The commands are inferred.** A pull request that ran two adds and a change is replayed as adds then changes. Adds and changes to different records commute, and the bytes agree, but the order within the pull request is not known.
- **Older history is not covered.** Four merges between 2026-11-02 and 2026-11-16 were screened out because their history does not state a replayable command, not because Python failed on them: #248 (thirteen batches of which eleven have a `batch.jsonl` that is no longer what was added, by up to all of their lines), #238 (three records added under a batch folder whose file lacks them), #236 (577 rows added with changes already recorded, so an add and a change to the same record inside one pull request) and #230 (`added_in` is `enchant-v3-20261102`, which is not a path). No merge before #227, of 2026-11-01, was tried.
- **A crash between two file writes is not undone**, here or in the TypeScript: both restore on an error they catch, not on a process that dies.
- **The date cannot be set from the command line.** `plan_change` and `plan_changes_file` take it as an argument, which is how the replay and the tests fix it.

## TypeScript behaviours found, not changed

`rewire-benchmark-data` was read and not touched.

- `records change` in both forms writes a record that `records check` would refuse. The SHACL step is the only check between the edit and the store.
- A record edited in place into another kind, then recorded with `records change`, ends up in two files: the new kind's, and its old line in the old kind's. The command reports success.
- Two lines with one ID are merged into the later one by `records change`, with no message.
- `1e400` in a record is stored as `null` by `add` and by both forms of `change`, with the digest of the `null` line.
- A provenance row without a `changed_by` list fails `records change` with a `TypeError` from `push`, after every other check has passed.
- `records add` and `records change` rewrite lines of records they were not asked about, whenever a stored line is not exactly what `JSON.stringify` writes for it.
- A changes file named with a relative path is named that way in every refusal, so the same refusal reads differently from another folder.
