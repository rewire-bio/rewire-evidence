`canonical.js_value` is new. It puts a value in the one form JavaScript holds it in: `1.0` and `1` are one number, an integer above 2^53 is the double nearest to it, and an object lists its integer-like keys first. `check_record` runs it first, so two parsed records are equal in Python exactly when JavaScript writes them the same.

## What a parse does to a record

This is what a record's identity rests on, so it is stated in full. All of it is recorded from zod, not read from its documentation.

- The nine top-level members come out in declaration order: `id`, `kind`, `name`, `description`, `status`, `facets`, `source_ids`, `links`, `attributes`.
- Each link comes out as `relation` then `target_id`, and any other member of a link is dropped. The link is not a strict object.
- Keys inside `facets` and `attributes` keep the order they were written in. Sorting the keys inside `attributes` would change 86,462 of the 93,216 stored records. Sorting `facets` would change none today, because every stored record already has them in order.
- A member named `__proto__` directly inside `facets` or `attributes` is dropped, whatever it holds. At the top level it is an unrecognised key. Deeper inside an attribute value it is kept.
- An unknown top-level key is refused, with `unrecognized_keys`.
- Numbers are whatever `JSON.parse` made of them: `1.0` is written `1`, `-0` is written `0`, `12345678901234567890` is written `12345678901234567000`.

## The rule identifier

zod has no rule names. An issue has a code, a path and a message, and the code with the path is what identifies the rule: `invalid_type:links.0.relation`. `schema.Issue.rule` is that string. The tests compare all three for every issue of every refused input, in zod's order, so the message is held too.

For the vocabulary loader and the reference checks the TypeScript throws a plain `Error`, so the message is the only identifier there is, and it is compared whole.

## The oracle

Two things, both from the TypeScript.

1. The committed records. Each must be accepted and written back as the line it was read from.
2. What the data repository's own code does, recorded by `scripts/fixtures/record_schema_fixture.mjs` in the `fixtures` job in CI. The job checks out the store at `STORE_REF`, runs `npm ci` there and runs the script with `tsx`, so the schema is the real `recordSchema` and the Turtle parser is the real n3. It writes three files and fails if a committed one differs:
   - `tests/fixtures/record-schema.json`: 299 inputs to `recordSchema.safeParse` as JSON text, 90 accepted with the bytes and digest zod's output serialises to, 209 refused with every issue. 68 stored records with their keys moved, with the digest after parsing. The kinds, statuses and relation rules. `relationAllows` for every relation and every pair of kinds, `currentRelation` for every kind and every older name, and cases for `normalizeRecords` (8), `publicRecords` (7) and the reference checks of `validateRecords` (20).
   - `tests/fixtures/vocabularies.json`: 40 small vocabularies through `loadSchemes`, 26 of them refused, and 31 sets of records through `controlledValues` and `validateVocabularies`.
   - `scripts/expected/store-schema.json`: what the TypeScript measures on the pinned store itself. `loadRecords` returned, so it accepts all 93,216 records. The file holds the counts below, each scheme's statements and concepts as n3 reads them, and the message for a bad concept seeded in each of the 20 controlled fields.

Nothing was installed on a developer machine to make these. The first recording was made by running the job and committing its `schema-fixtures` artifact.

## What ties a run to the pinned commit

The store-level expectation is not measured by this library and pinned. It is recorded by the TypeScript at `STORE_REF`, it names that commit, and CI refuses to run the gate unless `STORE_REF`, the checkout, `store-layout.json` and `store-schema.json` all name one commit. A checkout with a record removed or a concept edited fails on the recorded counts and digests even where every check the store can make of itself still passes, and `tests/test_conformance.py` shows both.

A pin bump therefore needs no hand-copied numbers for this gate: change `STORE_REF`, let the `fixtures` job fail, and commit its artifact.

## Where Python is stricter, or different

- The schema gate requires the committed line back. `loadRecords` does not: it hashes the parsed record, so a stored line with its top-level keys out of order passes `records check` while not being the line the writer would write. `records.load_records` follows the TypeScript. The gate reports such a line.
- `relation_allows` returns False for a name that is no relation. See the first TypeScript finding.
- `controlled_values` refuses a row whose `facets` or `attributes` is not an object, where the TypeScript fails with a `TypeError` or reads through it.
- `vocab.scheme_files` returns nothing when `data/vocab` is a file. The TypeScript throws.
- `store.load_store` is unchanged and still knows nothing of the schema. `records.load_records` is the schema-aware loader. The layout gate's numbers do not move.

## Known gaps

- A number beyond every double. `{"a":1e400}` is read as infinity by `JSON.parse`, accepted by `recordSchema`, and written as `null` by `JSON.stringify`. `parse_record` accepts it and holds infinity, as the TypeScript does in memory, and `js_stringify` refuses to write it, as it has since P1. So this is the one recorded accepted case whose bytes Python does not produce. No stored record holds such a number.
- The wording of a Turtle syntax error is the parser's own. `load_schemes` refuses the same files n3 refuses in the two recorded cases, with rdflib's message.
- Statement order is rdflib's parser order, caught as the parser emits. It equals n3's for all 25 files. Turtle constructs none of those files use (collections, blank-node property lists) are not covered by that.
- zod's length check on `name` and `target_id` runs on any value with a `length`. The port follows it for every JSON value, including text read as a number the way JavaScript reads it, with 60 recorded cases. One input is left out: an object whose `length` is itself an object with its own `toString` or `valueOf` member. zod throws a `TypeError` there instead of returning issues. Python reports the type issue and a `too_small`.
- `validate_references` is the ID, source and link checks of `validateRecords` and no more. In the TypeScript a check that no member has a private field's name runs before them, and the rest run after. Those are P5, and until then `load_records` accepts records they would refuse. The attribute registry, derivations, descriptions and evidence concerns are P4.
- `normalize_records` works on rows, not on `Record`, because the releases it reads use relation names the current schema refuses.
- A value nested deeper than Python will recurse, several hundred levels, is refused by `check_record` as `nested too deeply`. zod does not walk `attributes`, so Node accepts it. `js_stringify` already refuses such a row at about 450 levels.
- rdflib is this package's first runtime dependency (7.6.0 in `uv.lock`, the version the data repository's KG build pins).
- The `fixtures` job checks out the data repository and installs its dependencies on the runner on every run. The whole job takes under a minute: about 20 seconds for the checkout, 3 for `npm ci` from the cache and 20 for the recording, most of which is `loadRecords` over the store.

## Found in the TypeScript, not changed

- `relationAllows` in `shared/omics/relations.ts` looks the relation up on a plain object, so for `toString`, `constructor`, `__proto__` or `hasOwnProperty` it finds a member of `Object.prototype` and throws `Cannot read properties of undefined (reading 'includes')`. Nothing reaches it with such a name today, because `recordSchema` refuses an unknown relation first. A caller that skipped the schema would crash and not get `false`.
- zod drops a `__proto__` member of `facets` or `attributes` without an issue. A batch holding one is accepted, and the record stored and hashed is the record without it.
- A link is a plain `z.object`, so an extra member of a link is dropped without an issue. `scripts/kg/draft-block.ts` describes the same link to rdf-kg-mcp as `additionalProperties: false`, which refuses it. The two disagree.
- `draft-block.ts` also gives `source_ids` items `minLength: 1`. `recordSchema` accepts an empty source ID, and `validateRecords` then reports it as `Missing source  for <id>`.
- `validateVocabularies` breaks out of the loop over one record's values at 20 problems, not out of the loop over records. Each later record adds one more problem before breaking, so 30 records with two bad values each report 40 problems. The limit was probably meant to bound the message.
- `recordSchema` accepts a name that is one space, a link target that is one space, and a number beyond every double in `attributes`, which it then writes as `null`. A later validator may refuse some of these. The schema does not.
- With two records under one ID, `normalizeRecords` reads a claim's subject as the kind of the later one. `validateRecords` refuses duplicate IDs, so this matters only for a snapshot nothing validated.
- zod's `invalid_value` message for `kind` and `status` lists the options and never says what was received, so a wrong kind and a missing kind give the same issue.
