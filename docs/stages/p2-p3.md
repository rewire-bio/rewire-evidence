`canonical.js_string` is new: a JSON value as JavaScript joins it into text, which is how the TypeScript prints a scheme that `mapping.json` gives as something other than text.

`canonical.js_value` is new. It puts a value in the one form JavaScript holds it in: `1.0` and `1` are one number, an integer above 2^53 is the double nearest to it, and an object lists its integer-like keys first. `check_record` runs it first, so two parsed records are equal in Python exactly when JavaScript writes them the same.

## What a parse does to a record

This is what a record's identity rests on, so it is stated in full. All of it is recorded from zod, not read from its documentation.

- The nine top-level members come out in declaration order: `id`, `kind`, `name`, `description`, `status`, `facets`, `source_ids`, `links`, `attributes`.
- Each link comes out as `relation` then `target_id`, and any other member of a link is dropped. The link is not a strict object.
- Keys inside `facets` and `attributes` keep the order they were written in. Sorting the keys inside `attributes` would change 86,462 of the 93,216 stored records. Sorting `facets` would change none today, because every stored record already has them in order.
- A member named `__proto__` directly inside `facets` or `attributes` is dropped, whatever it holds. At the top level it is an unrecognised key. Deeper inside an attribute value it is kept.
- An unknown top-level key is refused, with `unrecognized_keys`.
- Numbers are whatever `JSON.parse` made of them: `1.0` is written `1`, `-0` is written `0`, `12345678901234567890` is written `12345678901234567000`.

## The rule identifier

zod has no rule names. An issue has a code, a path and a message, and the code with the path is what identifies the rule: `invalid_type:links.0.relation`. `schema.Issue.rule` is that string. The tests compare all three for every issue of every refused input, in zod's order, so the message is held too.

For the vocabulary loader and the reference checks the TypeScript throws a plain `Error`, so the message is the only identifier there is, and it is compared whole.

## What ties a run to the pinned commit

The store-level expectation is not measured by this library and pinned. It is recorded by the TypeScript at `STORE_REF`, it names that commit, and CI refuses to run the gate unless `STORE_REF`, the checkout, `store-layout.json` and `store-schema.json` all name one commit. A checkout with a record removed or a concept edited fails on the recorded counts and digests even where every check the store can make of itself still passes, and `tests/test_conformance.py` shows both.

A pin bump therefore needs no hand-copied numbers for this gate: change `STORE_REF`, let the `fixtures` job fail, and commit its artifact.

## Reading Turtle

`vocab.ts` reads each scheme with n3, and a vocabulary is whatever n3 makes of the file. n3 is not a strict reading of the Turtle grammar, and the first version of this stage read the files with rdflib, which agreed with n3 on the 25 committed files and on little else. `turtle.py` replaces it: a port of n3 1.17.4's `N3Lexer.js` and `N3Parser.js` as they run with `format: "Turtle"`, followed function by function. The N3, TriG, quad and RDF-star paths that Turtle mode switches off are left out. rdflib is no longer a dependency, and the package has none at run time.

What that reproduces, each recorded from n3:

- Which documents are refused, and in which words. A refusal is n3's own message, so `Unexpected "?x" on line 5.` and not a description of it. The lexer runs over the whole file first, so a fault of spelling anywhere is reported before a fault of grammar above it.
- The order statements are handed back in, including lists and blank nodes, which n3 emits when it closes them.
- A number or a boolean keeps the spelling it was written in: `01`, `1.e3`, `"TRUE"^^xsd:boolean`. A language tag is lowercased. `xsd:string` is no datatype.
- An escaped surrogate pair is one character. A code point above U+10FFFF in a `\U` escape comes out as the two units JavaScript's arithmetic makes of it.
- A relative IRI with no base declared stays relative: `<rel>` is `rel`. One that starts with a slash is joined to a value n3 never set, and reads `undefined/a`. `@base` and `BASE` are resolved as n3 resolves them, dot segments included.
- A file is decoded as Node decodes it. A byte that is not UTF-8 becomes U+FFFD, which n3 allows in a name, and a byte order mark at the start is dropped.
- Blank nodes are named from n3's two counters, `b0_x` for a label and `n3-0` for a node without one. Both are global to the JavaScript process, so here they are a value passed in, `turtle.BlankLabels`. The default is a process that has parsed nothing, which is what `records check` is, so a refusal that names a blank node names it as that command would. Every recorded case states where the counters stood.
- n3 goes on reading after a bracket that closes nothing, and in a few places reads a member of a value that is missing, which JavaScript throws as a `TypeError`. Both are kept, the second in V8's words.

Three things are JavaScript's and not n3's. The text is held as UTF-16 units, because n3's patterns are written over units. Every pattern spells out what `\s`, `\d`, `$` and `.` mean in JavaScript, which is not what they mean in Python. And case-insensitive matching is written out letter by letter, because Python's would let U+017F stand for `s`.

While the port was written it was compared with a scratch install of n3 1.17.4 alone, nothing of the data repository: about 750,000 damaged and token-sequence documents, and every character of the Basic Multilingual Plane in 26 places a pattern looks at one, 1,650,896 documents, with no disagreement left. Those runs are not in CI and are not the acceptance. The committed corpus is, and the store's 25 files by digest.

## What each gate catches

All three gates exit 0 when everything reproduces, 1 on a disagreement and 2 when the run could not be made. A store, a vocabulary or an expectation that cannot be read, a report that cannot be written, and anything else the operating system refuses are each one line and exit 2. Before this stage was reviewed several of those left with a traceback and exit 1.

The schema gate on its own does not hold every byte of the store. What it sees:

- A record whose value was edited no longer matches its provenance digest, and a line moved out of ID order or into another file is misplaced. `load_records` refuses both, so each is a problem. A removed record or concept changes the recorded counts.
- A blank line, and a missing or doubled final newline, are dropped before a record is read. The layout gate compares every file with its pinned bytes and refuses them.
- A record edited together with its provenance row agrees with itself. It passes the schema gate and the digest gate unless it moves a count, and only the layout gate's pinned bytes refuse it.
- The digest gate passes on the records it finds. A record removed with nothing else changed is caught by the schema gate's counts, the layout gate's counts, and the workflow's comparison of the digest gate's figure with `STORE_RECORDS`.

`tests/test_conformance.py` holds each of those cases.

## Where Python is stricter, or different

- The schema gate requires the committed line back. `loadRecords` does not: it hashes the parsed record, so a stored line with its top-level keys out of order passes `records check` while not being the line the writer would write. `records.load_records` follows the TypeScript. The gate reports such a line.
- `relation_allows` returns False for a name that is no relation. See the first TypeScript finding.
- `controlled_values` refuses a row whose `facets` or `attributes` is not an object, where the TypeScript fails with a `TypeError` or reads through it.
- A `mapping.json` JavaScript cannot read, with a section or a term that is null or missing, is refused when it is read. The TypeScript throws a `TypeError` at the first record it checks, and with no records never notices. Every other shape is read as the TypeScript reads it: a term that is not an object has no scheme, a scheme that is false, zero or empty is none, a section that is a list is read by position, and a scheme that is not text is never found and is printed as JavaScript prints it.
- A scheme file or a `data/vocab` that the operating system will not open is refused by both, in different words: Node's `EISDIR` and `ENOTDIR` messages against Python's. These are the two vocabulary loads compared on the refusal alone.
- The search for `skos:broader` loops keeps its own stack. Node recurses, and loads the recorded chain of 1,500. Somewhere past that Node's stack gives out and Python's does not. Where was not measured.
- `store.load_store` is unchanged and still knows nothing of the schema. `records.load_records` is the schema-aware loader. The layout gate's numbers do not move.

## Gaps from P1 that this closes

- There is now a schema. `records.load_records` parses each line before it is placed and hashed, and the gate shows key-order normalisation works on all 93,216 records.
- `KINDS` moved from `store.py` to `schema.py`, and a test holds it, the statuses, the member order and the relation rules equal to what the TypeScript declares, as recorded in `tests/fixtures/record-schema.json`. A change to any of them in the data repository fails the `fixtures` job at the next pin bump.

## Known gaps

- A number beyond every double. `{"a":1e400}` is read as infinity by `JSON.parse`, accepted by `recordSchema`, and written as `null` by `JSON.stringify`. `parse_record` accepts it and holds infinity, as the TypeScript does in memory, and `js_stringify` refuses to write it, as it has since P1. So this is the one recorded accepted case whose bytes Python does not produce. No stored record holds such a number.
- The Turtle port is held to a corpus, and a corpus is not a proof. It is n3 1.17.4 that was ported. The tests require the fixtures to name that version, so a data repository that moves to another n3 fails the `fixtures` job on any behaviour the corpus covers, and the port then has to be read against the new source.
- Three places where the port states something n3's source does not. Before the first statement n3 holds its subject and object as `undefined` and the port holds them as it holds `null`. No document was found on which that shows. One state of n3's parser, a blank node closed as a predicate, is reached only in N3 mode. It is kept and tested directly, not through a document. And a list is assumed to be read only inside the context saved for it, which the port relies on where n3 would read a member of `undefined`.
- A document is taken to be text read from a file. A string holding half of a surrogate pair, which no file decodes to, was not compared with n3.
- zod's length check on `name` and `target_id` runs on any value with a `length`. The port follows it for every JSON value, including text read as a number the way JavaScript reads it, with 60 recorded cases. One input is left out: an object whose `length` is itself an object with its own `toString` or `valueOf` member. zod throws a `TypeError` there instead of returning issues. Python reports the type issue and a `too_small`.
- `validate_references` is the ID, source and link checks of `validateRecords` and no more. In the TypeScript a check that no member has a private field's name runs before them, and the rest run after. Those are P5, and until then `load_records` accepts records they would refuse. The attribute registry, derivations, descriptions and evidence concerns are P4.
- `normalize_records` works on rows, not on `Record`, because the releases it reads use relation names the current schema refuses.
- A value nested deeper than Python will recurse, several hundred levels, is refused by `check_record` as `nested too deeply`. zod does not walk `attributes`, so Node accepts it. `js_stringify` already refuses such a row at about 450 levels.
- The `fixtures` job checks out the data repository and installs its dependencies on the runner on every run. The whole job takes about a minute: 20 seconds for the checkout, a few for `npm ci` from the cache and 25 for the recording, most of which is `loadRecords` over the store.

## Needs the owner

- `main` has no branch protection and the repository has no rulesets, so a pull request can merge with either job red or still running. `gh api repos/rewire-bio/rewire-evidence/branches/main/protection` answers 404 and `.../rulesets` answers an empty list. The gates are enforced inside the workflow and nothing requires the workflow. Requiring `checks` and `fixtures` on `main` is a repository setting, which this workstream does not change.

## Found in the TypeScript, not changed

- `relationAllows` in `shared/omics/relations.ts` looks the relation up on a plain object, so for `toString`, `constructor`, `__proto__` or `hasOwnProperty` it finds a member of `Object.prototype` and throws `Cannot read properties of undefined (reading 'includes')`. Nothing reaches it with such a name today, because `recordSchema` refuses an unknown relation first. A caller that skipped the schema would crash and not get `false`.
- zod drops a `__proto__` member of `facets` or `attributes` without an issue. A batch holding one is accepted, and the record stored and hashed is the record without it.
- A link is a plain `z.object`, so an extra member of a link is dropped without an issue. `scripts/kg/draft-block.ts` describes the same link to rdf-kg-mcp as `additionalProperties: false`, which refuses it. The two disagree.
- `draft-block.ts` also gives `source_ids` items `minLength: 1`. `recordSchema` accepts an empty source ID, and `validateRecords` then reports it as `Missing source  for <id>`.
- `validateVocabularies` breaks out of the loop over one record's values at 20 problems, not out of the loop over records. Each later record adds one more problem before breaking, so 30 records with two bad values each report 40 problems. The limit was probably meant to bound the message.
- `recordSchema` accepts a name that is one space, a link target that is one space, and a number beyond every double in `attributes`, which it then writes as `null`. A later validator may refuse some of these. The schema does not.
- With two records under one ID, `normalizeRecords` reads a claim's subject as the kind of the later one. `validateRecords` refuses duplicate IDs, so this matters only for a snapshot nothing validated.
- zod's `invalid_value` message for `kind` and `status` lists the options and never says what was received, so a wrong kind and a missing kind give the same issue.
- `loadSchemes` lets n3's refusal through as it is, so a syntax error names a line and not the file it is in. With 25 files that leaves the reader to find it.
- n3 accepts text no reading of Turtle allows, and a vocabulary holding it loads: a statement inside a blank node after a dot (`[ :p :o ; . :x :y :z ]`), `^^<iri>` standing alone as an object, and U+FFFD as a letter of a name, so a file saved in the wrong encoding can load with concepts quietly renamed. A relative IRI with no `@base` is kept relative, and `</a>` becomes `undefined/a`.
- `@prefix p: <1a:b> .` makes n3 throw a `TypeError` where it meant to report an invalid IRI.
- A refusal that names a blank node (`concept <n3-12> is not ...`) depends on how many documents the process parsed before, so the same file gives a different message from a different command.
- `controlledValues` never checks the shape of `mapping.json`. A scheme given as a number is reported as a missing vocabulary file named after the number, and a term or a section that is null is a `TypeError` at the first record.
