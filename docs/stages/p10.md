# P10: layer derivation

Status: done for the 871 objects a public release mirrors. Measured on 2026-11-22 against `rewire-benchmark-data` at `91f76cf8e61cba9d6037a01a19c9aa3051184900`, with the manifest of `e70b112078c6ba72112155caf3b091e166a405c5`, the commit that wrote the layer registry.

With this stage `rewire-evidence layers build`, `check` and `thresholds` are `npm run layers -- build`, `check` and `thresholds`. Every text layer and table grid the data repository registers is derived by this library from the stored bytes.

The oracle is committed: `data/omics/layers/registry.jsonl`, 2,595 lines, each a layer named by the SHA-256 of its bytes with ten counts read from them, and `unsupported.jsonl`, 245 lines. The gate derives every layer again and requires each committed line whole, not only its hash.

## Three things the oracle decided

**The registry is older than the manifest beside it.** A registry row copies `store`, `visibility` and `source_ids` from the manifest row of its object. The registry was last written at `e70b112` on 2026-11-19. On 2026-11-20 commit `f550406` recorded R2 as the home of every object, so at the pinned commit all 1,167 manifest rows say `store: r2` and every registry row still says `github-release` or `local-cache`. `npm run layers -- check` therefore cannot pass at the pinned commit, with the TypeScript or with this. The gate takes the rows it copies from the manifest of `e70b112`, held by digest in `scripts/expected/store-layers.json`, and requires byte equality. It then measures what the pinned manifest would write instead and pins the answer: all 2,240 checked rows differ, in `store` and in nothing else. A row that differed in any other member would fail the gate.

**The bytes are not in a checkout.** `scripts/fetch_public_objects.py`, whose work is `publicobjects.py`, fetches the release asset of every row that is public and names `github-release` as a mirror, 871 objects and 665,955,335 bytes, into a folder that CI caches on the digest of the manifest. It keeps the bytes it receives and never compresses. A public object missing from the folder fails the gate. A request that fails is made again, up to four times, and that includes a response that ends early, which Python raises as neither an `OSError` nor a `URLError`.

**A PDF layer is not a function of the bytes and the poppler version alone.** The registry names `pdftotext version 26.08.0`. No package index serves that release: Homebrew is at 26.11.0, conda-forge has 26.07.0 and 26.09.0, and apt is older. CI builds it from the source tarball, held by SHA-256, with poppler-data 0.4.12. Built on a macOS arm64 runner it writes the committed bytes for all 142 PDF rows of the public objects. Built from the same source on Linux it does not. Over the 110 public PDFs stored as they are:

The last row was not measured with poppler-data in the prefix. Where a layer differs it is by 7 to 2,001 bytes in a layer of 110,000 to 510,000, and one differs with the same length. The cause was not determined. That fused multiply-add moves six rows on x86-64 points at floating point in the layout, and nothing here confirms it.

So the `layers` job runs on `macos-15`, and the gate refuses to run on any pdftotext or pdfinfo whose version line is not the registry's release. The Linux rows are not in the gate. They are the measurement that says where it can run.

A version line is a precondition and not the proof, as the table shows. The proof is the gate: all 142 PDF rows of the public objects derived again and required whole, with the page count pdfinfo gives.

What is pinned of the build is the two source tarballs, by digest, and the recipe, `scripts/build_poppler.sh`, whose digest is in the key of the build's cache, so a changed flag builds again. What is not pinned is the runner image, `macos-15` as GitHub serves it, and the Homebrew libraries the build links against and loads on each run. The job writes the image version and the library versions into its summary. If the gate goes red on the PDF rows with no commit here, that is the first place to look: compare the summary with the last green run, then delete the `poppler-` cache and compare again.

## Where JavaScript is the specification

`tests/fixtures/layers.json` is recorded from the TypeScript by `scripts/fixtures/record_layers_fixture.mjs` in the `fixtures` job, on cases from `layers_cases.mjs` that the stored objects have no example of: 908 cases in 28 sections, and 32 command runs on four small trees. Every one is replayed.

- **A string is UTF-16 units.** `classify` reads the first 4,096 units, not characters, and a recorded case puts the cut inside a comment of emoji where the two readings disagree. The sheet limit counts units. A cell's offsets in a grid are characters, and are recorded on tables holding characters beyond U+FFFF.
- **UTF-16 input can hold half a surrogate pair.** Node keeps it, writes U+FFFD for it in the layer, and counts it as one character. Big-endian UTF-16 of an odd length is refused by `swap16`, in Node's words, and the object is unreadable rather than unsupported.
- **`\p{L}`, `\p{Nd}` and `\s` follow Node's Unicode version.** `metrics_of` reads the recorded sets, as the locator patterns do, and a recorded case counts every code point.
- **`Number.parseInt` reads a prefix.** A span of `" 3 "` is 3, `"1.9"` is 1, and 400 nines is an infinity, which is not a count of cells. It reads a number however many zeros open it: `&#` then 5,000 zeros then `65;` is `A`. Python's `int` refuses more than 4,300 digits whatever their value, so `js.parse_int` drops the zeros first. Recorded for a character reference, a `colspan`, a shared string index and a row number.
- **Every refusal is caught, because every error is.** `layerOf` and `officeLayer` catch whatever the normaliser throws and write its message as the reason. The port catches `LayerFailure`, so each `throw` in the TypeScript has to be one. `columnLabel` was not: a sheet with a value that no cell holds has a last row and no column, the TypeScript writes `xlsx normaliser failed: 0 is not a column number` to the unsupported file, and the port ended `layers build` in a traceback. It is recorded now, through `layerOf`, the registry build and the command.
- **The two files are ordered by UTF-16 unit**, in the path and in the reason. No stored object has paths the two orders rank differently, so it is recorded on a zip whose members are named with U+E000, U+FFFF and a character beyond U+FFFF.
- **A tar name ends at a NUL only if nothing after it ends a line**, because `.` stops at a line terminator.
- **An attribute named `__proto__` sets nothing** on the plain object the Office scanner keeps attributes in.
- **zlib's words are not reproduced.** A problem line that quotes zlib, for a member that will not inflate, says so in this library's words after the colon. No committed file holds such a line: `problems` reaches no registry row.

`tests/fixtures/js-semantics.json` gained `parse_int`, `buffer_text`, `until_nul`, `upper_ascii` and `inflate_raw`, recorded with built-ins only.

## Errors only a runtime raises

The catch in the port is narrow on purpose. The TypeScript's `catch` also takes errors that JavaScript's runtime raises and no line of it throws: a string past V8's length limit, a call stack too deep. It would write those as reasons too, in V8's words, at sizes that are V8's. The port does not reproduce them. A Python error that is not a `LayerFailure` ends the run with a traceback and writes neither file, which is the safer of the two ways to be wrong: a build never writes a reason the TypeScript would not have written. Every `throw` statement under `shared/archive/layers` was read against the port for this, and the calls that can throw without one (`fromCodePoint`, `swap16`, `inflateRawSync`, `gunzipSync`, `JSON.parse`, `repeat`) are each guarded, caught where the TypeScript catches them, or outside the derivation. Two runs of generated input looked for anything else: 805,000 workbooks, documents and pages assembled from markup tokens, and 1,487,000 corrupted copies of the recorded archives and packages, through `layers_of_object`, `office_layer` and `zip_entry_names`. Nothing but the refusals above came out.

## Property tests

- `tidy_traced` equals a transcription of the TypeScript's loop one character at a time, and is idempotent.
- The scan a grid is built by gives the text the text layer holds, for any sequence of table markup, and every cell's offsets select its text.
- `metrics_of` equals a transcription of the TypeScript's loop over Node's recorded sets.
- A zip or a tar written by the standard library expands to its files.
- Any bytes have a layer tree or are refused in Node's words, and a layer's `identity` is true exactly when its bytes are the object's.
- A column label names its number, an escaped cell holds no control character, and UTF-8 text is its own layer.

## TypeScript behaviour noted, not changed

- `layers -- check` fails at the pinned commit, for the reason above. Measured with this port's command over all 1,167 objects: at the pinned commit it prints `data/omics/layers/registry.jsonl is not what the store produces` and `1 problems`, and at `e70b112` it prints `2595 layers reproduce`. That the TypeScript's command does the same is by reading it, not by running it. The registry needs regenerating after any manifest write that changes `store`, `visibility` or `source_ids`, or the three members should not be copied into it.
- `pdf-text-layer@1` does not reproduce across platforms at one poppler version, measured above. The data repository's `label-measure` workflow installs `poppler-utils` from apt on Ubuntu, so a PDF layer derived there is not the registered one, and `layerText` will refuse it.
- `readPinnedPdfText` gives a conversion 30 seconds, and a PDF that takes longer is recorded as having no layer. Whether a slow PDF has a layer therefore depends on the machine. The slowest stored PDF took 3.2 seconds here.
- `expandContainer` is caught by `layerOf` and by `officeLayer`, and can throw in neither place for bytes `classify` called a container. It can throw in `officeLayer` called on its own, for a file whose central directory names a workbook and whose first bytes are not `PK`.
- `encodingOf` calls bytes that open with a UTF-8 byte order mark text without checking what follows, so a binary file with that prefix gets a text layer of U+FFFD.
- A workbook with a value that no cell holds, `<row r="3"><v>5</v></row>`, has no layer: the sheet has a last row and no column, and `columnLabel(0)` throws. The reason written is `xlsx normaliser failed: 0 is not a column number`, which names the fault in the code and not in the file. The port writes the same line.
- The Office scanner's attribute pattern takes time that grows with the square of a tag's length when the tag holds a long run of name characters and no `=`. A tag of 40,000 letters took 0.7 seconds in Node 26.7 and 5.7 seconds in Python, so a megabyte is minutes in one and about an hour in the other. The pattern is the TypeScript's and the port keeps it. A corrupted copy of a recorded workbook reached it, and no stored object does.
- A grid's `candidateHeader` and `place` and the document reader agree with the port on every recorded case. No fault was found in them.

## Tests that hold a boundary

Each of these was added because changing the code left every earlier test passing.

- A sheet of exactly 4,096 columns has a layer, and one of 4,097 is refused.
- The limit on what pdftotext writes is on standard error as well as standard output.
- A `</t>` that closes nothing does not stop the next shared string being kept.
- Two halves of a character that a removed tag leaves side by side are one character in the count.

Two more were looked at and left, because no input can tell the two forms apart. In the markup scanner `opened > index` guards a call that returns at once for empty text. In the grid builder `r < len(table.rows)` keeps out of a map the cells below the last row, and the map is read only for header rows, which are rows of the table.

## Known gaps

- The 355 registry lines and 13 unsupported lines of the 296 restricted objects are not checked in CI.
- The gate reads a committed row through the registry's schema and stops with the line's number at one that is not a row. It does not say more than the first refusal.
