## Where the writers are stricter than the TypeScript

The TypeScript writers trust their callers, because every caller runs `recordSchema.parse` first. Nothing runs first here until P2, so the writers check what the layout itself depends on. None of this changes a byte written for valid input.

- A kind outside `store.KINDS` is refused. `kindPath` builds a path from whatever kind it is given, so `../../../escaped` would be written outside the store and `banana` would start `data/entities/bananas.jsonl`.
- `write_store`, `write_kind`, `write_family` and `append_rows` place, order and serialise every row before they write any file. A refused row leaves the disk as it was.
- Two rows with one key are refused in a uniquely keyed family (records, provenance, manifest). A file holding two would fail `load_store` and the gate.
- A row that is not an object, lacks a field it is placed or sorted by, or cannot be serialised is refused with its position: `record 3 (model-a)`, `provenance row 2`, `row 5`.

This is validate-then-write, not a transaction. The files are written one after another, and a run interrupted between two of them is not undone. The TypeScript handles that in `writeCheckedAgainstShapes`, which snapshots the store and restores it, and that is P6.

The foundations, for the whole package:

- 100% line and branch coverage of `src/rewire_evidence`, enforced in CI with `--cov-branch --cov-fail-under=100`. No line is excluded.
- `mypy --strict` over `src`, `scripts` and `tests`, with unreachable-code and redundant-expression warnings on.
- Ruff with every rule selected and a short ignore list, each entry with its reason, in `pyproject.toml`.
- Property tests with Hypothesis for the algebraic properties: a written number reads back as the same double, `canonical_json` ignores key order at every depth, `canonical_line` ignores it at the top level only, resharding is idempotent, and the logical digests do not depend on the shard layout.
- Every tool version comes from `uv.lock`.
- `scripts/fixtures/record_js_fixture.mjs` records both JavaScript fixtures with Node built-ins. CI runs it and fails if either file changes.

## JavaScript behaviour the store holds no example of

The store has no object with an integer-like key, no integer above 2^53 and no unpaired surrogate, so the oracle is silent on all three. Each was recorded from Node (`tests/fixtures/js-semantics.json`) and the library changed to match:

- A JavaScript object lists array-index keys (`"0"` to `"4294967294"`, no leading zero) first, in numeric order. `js_stringify` and `canonical_line` now do. `canonical_json` does not, because the TypeScript builds that string itself without making an object.
- An integer above 2^53 is written as the double nearest to it. `js_parse` reads one that way and `js_stringify` writes one that way. Before this change a Python `int` was written exactly, which JavaScript cannot do.
- An unpaired surrogate is written as a `\udXXX` escape, and a pair held as two code points is written as the one character it is.
- `js_parse` refuses `NaN` and `Infinity`, which Python's reader accepts.
- `js_parse` reads an integer literal of any length. Python refuses to convert one of more than 4,300 digits, and `JSON.parse` reads it as a double, which is infinity at that size.
- Text is hashed as Node hashes it: UTF-8 with U+FFFD in place of a surrogate that has no partner. `shardOf` hashes an ID that way, so `shard_of` and `sha256_hex` do too, where they used to raise `UnicodeEncodeError`.
- `object_shard` refuses a key that is not a lowercase SHA-256, as `objectShard` does.

## The oracle

Every committed file of the ten families, the placement of every row, and the 18 logical digests in release receipt `2026-11-20-72316db0764b`, which is the newest by `released_at`. The receipt carries no store revision, so the receipt ID and the store commit are pinned together in `scripts/expected/store-layout.json`.

## What ties a run to the pinned commit

Most of the gate compares a checkout with itself: a file is read, written again and compared. That proves the library writes what the store holds. It does not prove the checkout is the store that was measured, and outside the records and provenance, which are tied together by digests, a row edited into another valid row would pass.

Two things close that, both in `scripts/expected/store-layout.json`:

- Every count is pinned, so a checkout holding fewer rows fails.
- The SHA-256 of each family's files is pinned, taken over each file's path, length and bytes in the order the family lists them. A checkout whose bytes differ in any family fails and names the family.

The script does not ask git which commit is checked out, so it works on any folder holding the files. CI also compares `git rev-parse HEAD` with `STORE_REF` before it runs the gates.

The gate reports a file that sits among a family's files and that no family reads: anything in `data/archive/objects` other than the 16 shards, and a receipts file of either kind whose name is not exactly a date and the kind. Nothing reads such a file, so nothing else would notice it. There are none at the pinned commit.

The comparison is of whole files, so one equality covers the serialisation, the row order, the final newline and the absence of blank lines.

The table above is the serialiser held against the committed bytes in memory. The functions that write to disk are held against them too. The gate reads each committed file and hands its rows to the writer a caller would use, in an empty temporary folder:

- `write_family` and `append_rows` reproduce 100 of 100 files (199,585 lines).
- `write_store`, which is a second implementation of the record and provenance layout, reproduces 78 of 78 files.
- `reshard_store` over that copy places 93,216 records and leaves 78 of 78 files byte for byte.
- `reshard_store` over a second copy, laid out as the store was before it was sharded (one file per kind and one provenance file, each shard's lines in descending order), places 93,216 records and produces 78 of 78 committed files. The reshard of a copy already in its layout cannot show that `reshard_store` sorts, and this one can.

Exit status, for both gates: 0 when everything reproduces, 1 on any disagreement, 2 when the run could not be made (no checkout, no expectation, no release receipt). A record that does not match its provenance row is a disagreement: every such record is listed, the tables are still printed and the `--json` report is still written.

Controls, run once by hand against the same checkout, show the gate can fail:

- With one manifest row's `bytes` raised by one, one registry metric raised by one, one bit flipped in a model's name and two stray files added, the layout gate exits 1 with nine problems: the two strays, the entity digest against the receipt, the record against its provenance row, two counts, and the pinned digests of the entities, manifest and layer registry families. The digest gate exits 1 naming the record. Before the digests were pinned the manifest and registry edits passed.
- Under `canonical_json` the layer registry reproduces 0 of 2,595 rows, because its nested `metrics` object is not in key order. The manifest has no nested object and passes under either, so it cannot catch that mistake. `tests/test_parity.py` holds the same control on a small store.
- Python's `json.dumps` gets 4 of 12,046 entity lines wrong, the four `1e-05` values.

## Known gaps

- No schema. `load_store` is `loadRecords` without `recordSchema.parse` and the validators. It hashes a record as its line was read, so it proves the stored bytes are stable under this library and does not prove that key-order normalisation works. That is P2.
- The families are layout and bytes only. Manifest and receipt schemas, `upsertRow`, `markHome`, `markMirror` and `markRemoved` are P9.
- `write_kind`, `write_store` and `write_family` leave a file alone if it receives no row, as the TypeScript does. Removing the last record of a shard needs `reshard_store`.
- Three sets of files have no canonical form and belong to no family: the 2026-09-19 audit receipts, `data/omics/search-ledger.jsonl` and `data/omics/scope-audit.jsonl`. They were written by hand and by `json.dumps` in mixed formats. A port may append to them and must never rewrite a line.
- The licence candidates file is sorted by `source_id` by the resolver, not by the line that writes the file. The family sorts it, which is the same bytes for the committed file and a deliberate choice for any other input.
- `js_parse` turns `1e999` into infinity as `JSON.parse` does, and `js_stringify` then refuses it where JavaScript would write `null`. A writer refuses the row by position and the gate reports the line as one that cannot be written. No store file holds such a number.
- A row nested more than about 450 levels deep cannot be written, because the serialisers recurse and Python stops them. Node 26 reads and writes 100,000 levels. The row is refused by name (`nested too deeply`) and not with a traceback. No store file is nested more than a few levels.
- `store.KINDS` is a copy of `entityKinds` at the pinned commit, checked by nothing but the gate finding all 17 kinds in use. P2 should take it from the same recorded contract as the rest of the schema.
- The gate peaks at about 1.5 GB of memory, almost all of it the provenance map and the lines held for a reshard. It writes three temporary copies of the store's line files, about 700 MB together, and removes them. It runs in about 50 seconds.
- Nothing in the repository's settings requires the Checks workflow before a merge. See "Needs the owner" below.
- `readProvenance` in the TypeScript keeps the last of two rows with one ID without complaint, and so does `read_provenance`. Both `loadRecords` and `load_store` catch it later, through the count check, and the gate catches it through the strict sort check on the provenance family.

## Needs the owner

- `main` has no branch protection and no ruleset, so a pull request can be merged while Checks is red or still running. Requiring the `checks` job on `main` is a repository setting, which this work does not change.

## Found in the TypeScript, not changed

- `kindPath` in `scripts/omics/records.ts` builds a file path from the kind with no check. Every caller parses with `recordSchema` first, so nothing reaches it today. A caller that skipped the schema could write outside the store.
- `writeGrouped` writes two rows with one ID without complaint. `loadRecords` refuses the file afterwards.
- `readProvenance` keeps the last of two rows with one ID. The count check in `loadRecords` catches it later.
