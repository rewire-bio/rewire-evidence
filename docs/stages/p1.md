The foundations, for the whole package:

- 100% line and branch coverage of `src/rewire_evidence`, enforced in CI with `--cov-branch --cov-fail-under=100`. No line is excluded.
- `mypy --strict` over `src`, `scripts` and `tests`, with unreachable-code and redundant-expression warnings on.
- Ruff with every rule selected and a short ignore list, each entry with its reason, in `pyproject.toml`.
- Property tests with Hypothesis for the algebraic properties: a written number reads back as the same double, `canonical_json` ignores key order at every depth, `canonical_line` ignores it at the top level only, resharding is idempotent, and the logical digests do not depend on the shard layout.
- Every tool version comes from `uv.lock`.
- `scripts/fixtures/record_js_fixture.mjs` records both JavaScript fixtures with Node built-ins. CI runs it and fails if either file changes.

## JavaScript behaviour the store holds no example of

The store has no object with an integer-like key, no integer above 2^53 and no unpaired surrogate, so the oracle is silent on all three. Each was recorded from Node (`tests/fixtures/js-semantics.json`) and the library changed to match:

- A JavaScript object lists array-index keys (`"0"` to `"4294967294"`, no leading zero) first, in numeric order. `js_stringify` and `canonical_line` now do. `canonical_json` does not, because the TypeScript builds that string itself without making an object.
- An integer above 2^53 is written as the double nearest to it. `js_parse` reads one that way and `js_stringify` writes one that way. Before this change a Python `int` was written exactly, which JavaScript cannot do.
- An unpaired surrogate is written as a `\udXXX` escape, and a pair held as two code points is written as the one character it is.
- `js_parse` refuses `NaN` and `Infinity`, which Python's reader accepts.
- `object_shard` refuses a key that is not a lowercase SHA-256, as `objectShard` does.

## The oracle

Every committed file of the ten families, the placement of every row, and the 18 logical digests in release receipt `2026-11-20-72316db0764b`, which is the newest by `released_at`. The receipt carries no store revision, so the receipt ID and the store commit are pinned together in `scripts/expected/store-layout.json`.

Two controls, run once by hand against the same checkout, show the gate can fail:

- Under `canonical_json` the layer registry reproduces 0 of 2,595 rows, because its nested `metrics` object is not in key order. The manifest has no nested object and passes under either, so it cannot catch that mistake. `tests/test_parity.py` holds the same control on a small store.
- Python's `json.dumps` gets 4 of 12,046 entity lines wrong, the four `1e-05` values.

## Known gaps

- No schema. `load_store` is `loadRecords` without `recordSchema.parse` and the validators. It hashes a record as its line was read, so it proves the stored bytes are stable under this library and does not prove that key-order normalisation works. That is P2.
- The families are layout and bytes only. Manifest and receipt schemas, `upsertRow`, `markHome`, `markMirror` and `markRemoved` are P9.
- `write_kind`, `write_store` and `write_family` leave a file alone if it receives no row, as the TypeScript does. Removing the last record of a shard needs `reshard_store`.
- Three sets of files have no canonical form and belong to no family: the 2026-09-19 audit receipts, `data/omics/search-ledger.jsonl` and `data/omics/scope-audit.jsonl`. They were written by hand and by `json.dumps` in mixed formats. A port may append to them and must never rewrite a line.
- The licence candidates file is sorted by `source_id` by the resolver, not by the line that writes the file. The family sorts it, which is the same bytes for the committed file and a deliberate choice for any other input.
- `js_parse` turns `1e999` into infinity as `JSON.parse` does, and `js_stringify` then refuses it where JavaScript would write `null`. No store file holds such a number.
- The gate peaks at about 1.2 GB of memory, almost all of it the provenance map and the result lines held for the logical digest.
