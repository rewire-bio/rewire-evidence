## Running a JavaScript pattern in Python

The grammar is its patterns, so the port stands or falls on running them as JavaScript does. Python's `re` reads the same syntax and differs in these places, each of which the store or the fixture reaches:

- `\p{L}` and `\p{N}` are not in `re`, and follow the Unicode version. Python 3.12 has Unicode 15.0 and the recorded Node has 17.0.
- Under the `i` flag JavaScript matches a letter with another by its own rule, which is one rule without the `u` flag and another with it. With both, `s` matches U+017F and `k` matches U+212A, `\w` and `\b` count those two as word characters, and `\p{L}` matches U+0345. Python's `re.IGNORECASE` has a third rule.
- `\s` is JavaScript's white space, which has U+FEFF and lacks U+001C to U+001F and U+0085. `\d` and `\w` are ASCII.
- `.` stops at four line terminators, and `$` is the end of the text only.
- Without the `u` flag a pattern sees UTF-16 units. `[^'"]{40,}` is satisfied by twenty characters beyond U+FFFF, and a match can end inside one.

`jsregex.py` reads a pattern as JavaScript writes it and writes it out again for `re`, with no flags. Every class, escape, dot and letter under `i` becomes an explicit class of ranges, and the ranges are data: `scripts/fixtures/pattern_requests.json` lists the 162 sets the library's patterns and the test patterns hold, each with the flags that decide it, and `scripts/fixtures/record_pattern_fixture.mjs` asks Node which characters each one matches and writes `src/rewire_evidence/data/pattern-classes.json`. A set under the `u` flag is over all 1,114,112 code points and one without it over the 65,536 units. Text is matched one character to a unit, and for a pattern with the `u` flag the units are paired up first and the result put back into units.

Two things Python does differently cannot be written away, so a pattern that has either is refused with `Unsupported`: a named group inside a repeat (JavaScript resets it on each pass and Python keeps the last value), and a repeat whose body can match nothing. So is everything the port does not use: unnamed groups, backreferences, `\B`, and the flags `m`, `s`, `y`, `d` and `v`. None of the grammar's patterns has any of these. 55 patterns are recorded as refused in `tests/test_jsregex.py`.

The patterns in `locator.py` are checked against the TypeScript's own. The recorder writes a copy of `locator.ts` that exports its unexported `TOKENS`, reads each pattern's `source` and `flags` from it, and removes the copy. A test requires the 28 in `TOKEN_SOURCES` to be those, character for character.

## The oracle

The store commits one coverage report of twelve rows. Totals cannot show that two parsers agree on what a locator says, so the oracle is recorded from the TypeScript, in CI, at the pinned commit:

- `scripts/expected/store-locators.jsonl.gz` holds one line for every result that has a locator, in the order `storedLocators` reads them: `{"id", "class", "coverage", "parsed", "rendered"}`, where `parsed` is the whole `ParsedLocator`. It is 52,278 lines, 39.3 MB as text and 2.6 MB compressed.
- `scripts/expected/store-locators.json` names the commit, the number of lines and their SHA-256 (`d9b60701...f7153f4f`), and holds the report `locator-cli.ts coverage` printed and wrote for the store, the committed report that equals it, and how the version 1 pattern splits the value-check rows.

gzip does not write the same bytes on every zlib, so the compressed file is never compared. The recorder rewrites it only when the lines inside differ, and the `fixtures` job fails if either file is not what the TypeScript produces.

`scripts/verify_store_locators.py` reads the locators from the checkout, not from the recording, writes the same line for each with this library, and requires:

1. every line to be the recorded line, byte for byte, and the lines together to have the recorded SHA-256;
2. the coverage report, as written and as printed, to be what the TypeScript's command wrote and printed, and the bytes of `maintenance/reports/locator-coverage-2026-11-18.tsv` in the checkout;
3. the version 1 pattern to accept a row of a `value-check.tsv` file exactly when `check-values` did not report it as `locator_not_parsed`, over 14 files, with the recorded counts.

CI pins the counts as well: 52,278 locators read and reproduced, 2,432 value-check rows read and agreed. A thinner checkout fails.

The store cannot test what it has no example of. It holds no character beyond U+FFFF, no letter that folds onto an ASCII one and no line separator. `tests/fixtures/locator.json` is the TypeScript's answer on 2,316 locators written for that: 94 by hand, the 39 of the data repository's own sample, and the rest put together from parts by a seeded generator, about one part in five with an awkward character dropped in. 101 hold a character beyond U+FFFF and 65 hold half of one. It also records `selectorRole` on 32 keys, `carriesNoAddress` on 29 words, `renderLocator` on 23 sets of typed fields, `verdictOf` on 572 parses built by hand, `tallyLocators` on 5 lists and 16 runs of the command.

## Measured result

- Gate: 52,278 of 52,278 stored locators are read as the TypeScript reads them, byte for byte. The report is the committed one, byte for byte: 40,464 fully addressed, 3,212 partially, 8,192 with residue, 410 unanchored. The version 1 pattern agrees with `check-values` on 2,432 of 2,432 rows, 1,881 parsed and 551 not.
- Fixture: all 2,316 recorded locators agree, in the parse, the class, the coverage, the rendering, the segments and the version 1 answer, with the members of each parse in the order JavaScript writes them. All 203 recorded matches of 65 patterns agree, and all 39 `toFixed` results.
- The command prints and writes what the TypeScript's prints and writes on the 8 recorded runs that succeed, exits 1 on the 3 that stop the TypeScript and 2 on the 4 it answers with its usage.
- Seeded faults: seven one-line changes to the grammar were each run against the tests and the gate. The tests fail on all seven. The gate fails on four (41 tokens to a segment in place of 40, a tie going to the later token, curly quotation marks not opening a quote, a line address not standing for a row) and passes three that the store has no example of (a closing bracket taking the depth below zero, Python's `lower`, Python's `strip`), which is what the fixture is for.
- Coverage: 100% of lines and branches of `src/rewire_evidence`, 5,870 statements and 2,148 branches, with no line excluded.
- Cost: the gate takes about 30 seconds.

Properties checked with Hypothesis:

- a match is a piece of the text at the place it names, replacing it with itself changes nothing, and replacing it with nothing removes exactly it;
- pairing units into characters undoes splitting characters into units;
- any text is read into fields whose verdict is the one `verdict_of` gives them, with no empty or untrimmed segment or residue, and reading it twice gives the same parse;
- text with no comma or semicolon is one segment;
- an ordinal after a row or column key does not change what the key names;
- a share in the report is within a twentieth of a percent of the true one and never the lower of two equally near;
- `fixed` is the exact value of the double rounded half up, by an independent calculation in decimal.

## Where the port differs, on purpose

- **`locator coverage --out` with no path is a usage error.** The TypeScript reads the missing path as no `--out` at all and writes the dated report.
- **A store that cannot be read is refused in one line, before anything is printed.** The TypeScript leaves with a stack trace and the same status, 1. A report that cannot be written is refused the same way, where the TypeScript has printed the table by then.
- **A result file that is not UTF-8 is refused.** Node reads the bytes it cannot decode as U+FFFD and goes on.
- **The stop on an empty match is not ported.** `consume` breaks when the leftmost match is empty. No token can match nothing, which a test holds, so the stop is never reached.
- **`render_locator` takes addresses as a list.** The TypeScript takes either `addresses` or an `address` and its `refines`, and `authored_addresses` makes the list from the second form.

## Known gaps

- **The zod schemas are not ported**: `spanSchema`, `locatorSchema`, `parsedLocatorSchema` and the four schemas of their parts. No record holds a span, and nothing in the store is checked against them. They belong with P11, which resolves spans.
- **Only the patterns the grammar uses can be run.** `jsregex` refuses the rest by name. A later stage that needs another construct has to add it and record cases for it.
- **A new pattern needs a recording before it runs.** Its sets have to be listed and recorded in CI, because the recording follows Node's Unicode version and no machine here is trusted to have the same one. A test fails while the list is stale.
- **The recorded lines are 2.6 MB in the repository**, and a pin bump replaces them.
- **The gates are still not required by the repository.** That is a repository setting.

## What a pin bump now takes

Bumping `STORE_REF` changes the stored locators. The `fixtures` job then fails, and its `schema-fixtures` artifact holds the new `store-locators.json` and `store-locators.jsonl.gz` to commit. `STORE_LOCATORS` and `VALUE_CHECK_ROWS` in `checks.yml` are pinned by hand.

## Found in the TypeScript, not changed

`rewire-benchmark-data` was read and not touched.

- **No locator is ever read as an XML cell.** `qual_layer` stands before `addr_xml` in the token list and matches at `XML` wherever `addr_xml` would, so it wins every tie. 806 stored locators say `XML row 6 column 4` or the like, and each has the row and column inside the text of a `layer` qualifier, with no `xml_cell` address. `renderLocator`'s `xml_cell` branch and the `DIRECT` rule for it are reached by no stored locator.
- **No locator is ever read as a `layer_line` qualifier**, for the same reason: `qual_layer` takes `text-layer line 12` whole. 1,499 stored locators say `text-layer line`.
- **103 stored locators have a segment the grammar stops reading at 40 tokens.** With the limit at 41 they parse differently.
- **A quote opened by a curly mark is closed only by a straight one.** `splitSegments` holds the open quote as `'` whichever mark opened it, so in `row 'a, b', column 'c'` written with curly marks the rest of the locator is one segment.
- **`--out` with nothing after it writes the dated report** and says nothing about the missing path.
- **`parse` with a first argument that is empty prints the usage**, whatever follows it.
