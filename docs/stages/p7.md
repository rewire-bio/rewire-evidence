## Running a JavaScript pattern in Python

The grammar is its patterns, so the port is right only if it runs them as JavaScript does. Python's `re` reads the same syntax and differs in these places, each of which the store or the fixture reaches:

- `\p{L}` and `\p{N}` are not in `re`, and follow the Unicode version. Python 3.12 has Unicode 15.0 and the recorded Node has 17.0.
- Under the `i` flag JavaScript matches a letter with another by its own rule, which is one rule without the `u` flag and another with it. With both, `s` matches U+017F and `k` matches U+212A, `\w` and `\b` count those two as word characters, and `\p{L}` matches U+0345. Python's `re.IGNORECASE` has a third rule.
- `\s` is JavaScript's white space, which has U+FEFF and lacks U+001C to U+001F and U+0085. `\d` and `\w` are ASCII.
- `.` stops at four line terminators, and `$` is the end of the text only.
- Without the `u` flag a pattern sees UTF-16 units. `[^'"]{40,}` is satisfied by twenty characters beyond U+FFFF, and a match can end inside one.

`jsregex.py` reads a pattern as JavaScript writes it and writes it out again for `re`, with no flags. Every class, escape, dot and letter under `i` becomes an explicit class of ranges, and the ranges are data: `scripts/fixtures/pattern_requests.json` lists the 163 sets the library's patterns and the test patterns hold, each with the flags that decide it, and `scripts/fixtures/record_pattern_fixture.mjs` asks Node which characters each one matches and writes `src/rewire_evidence/data/pattern-classes.json`. A set under the `u` flag is over all 1,114,112 code points and one without it over the 65,536 units. Text is matched one character to a unit, and for a pattern with the `u` flag the units are paired up first and the result put back into units.

Three things cannot be written away, so each is refused with `Unsupported`:

- **A named group inside a repeat.** JavaScript resets it on each pass and Python keeps the last value.
- **A repeat of something that can match nothing, `?` and `{0,1}` included.** Once a repeat has the fewest passes it needs, JavaScript gives up a pass that matched nothing and tries another way, and Python keeps the pass. On `e`, Node leaves the group of `/E(?<g>\b)?/i` unset and `re` sets it to the empty text. On `ssheet`, Node matches `ss` with `/(?:\w?[^x]{0,2}\b|\w?[^x]q{0,2})?/` and `re` matches nothing.
- **A pattern with the `u` flag that can match nothing, on text that holds a character beyond U+FFFF.** The specification looks for a match only where a character starts. Node 24.22.3 gives `/(?![^,;])/u.exec("a\u{1D400}")` the index 2, which is between the two units of the character, and the specification gives 3. That one case is recorded. The reading of it, which is not, is that V8 also looks between the units, where nothing that takes a character can match and a match of nothing can; the refusal is drawn from that reading and is wider than the one case. Node is the oracle, and Python cannot stand between the units of a character it holds whole. The same pattern runs on any other text. The refusal is made when the pattern is run, because it depends on the text, and a test requires every pattern of the grammar with the `u` flag to take at least one character, so the grammar is never refused. A `u` pattern that has to take a character is run on such text and is held there by the recorded cases alone.

So is everything the port does not use: unnamed groups, backreferences, `\B`, a character beyond U+FFFF written in a pattern with no `u` flag, and the flags `m`, `s`, `y`, `d` and `v`. None of the grammar's patterns has any of these, and none with the `u` flag can match nothing. 64 patterns are listed as refused in `tests/test_jsregex.py`, and 5 recorded matches are refused for the text they are run on.

`replace` is JavaScript's own loop over `search`, not `re.sub`. After a match of nothing JavaScript looks again one character further on. `re.sub` looks again at the same place for a match that is not empty, which a lazy repeat then gives it: `"x1y".replace(/[a-z]*?/g, "<>")` is `<>x<>1<>y<>` in Node and `re.sub` writes `<><><>1<><><>`.

The patterns in `locator.py` are checked against the TypeScript's own. The recorder writes a copy of `locator.ts` that exports its unexported `TOKENS`, reads each pattern's `source` and `flags` from it, and removes the copy. A test requires the 28 in `TOKEN_SOURCES` to be those, character for character. Nine of the eleven patterns `classifyLocator` runs are written inside the function, where no export reaches, so the recorder reads them off as the function runs: it notes the `flags` and `source` of every pattern tested on two locators that between them fall through every decision. A second test requires the eleven in `locator.py` to be those, in that order.

## The oracle

The store commits one coverage report of twelve rows. Totals cannot show that two parsers agree on what a locator says, so the oracle is recorded from the TypeScript, in CI, at the pinned commit:

- `scripts/expected/store-locators.jsonl.gz` holds one line for every result that has a locator, in the order `storedLocators` reads them. The command's `storedLocators` gives the locators without the IDs the lines carry and is not exported, so the recorder reads the result files with its own loop, then runs the command's function from a copy that exports it and stops if the two do not choose the same locators in the same order. Each line is `{"id", "class", "coverage", "parsed", "rendered"}`, where `parsed` is the whole `ParsedLocator`. It is 52,278 lines, 39.3 MB as text and 2.6 MB compressed.
- `scripts/expected/store-locators.json` names the commit, the number of lines and their SHA-256 (`d9b60701...f7153f4f`), and holds the report `locator-cli.ts coverage` printed and wrote for the store, the committed report that equals it, and how the version 1 pattern splits the value-check rows.

gzip does not write the same bytes on every zlib, so the compressed file is never compared. The recorder rewrites it only when the lines inside differ, and the `fixtures` job fails if either file is not what the TypeScript produces.

`scripts/verify_store_locators.py` reads the locators from the checkout, not from the recording, writes the same line for each with this library, and requires:

1. every line to be the recorded line, byte for byte, and the lines together to have the recorded SHA-256;
2. the coverage report, as written and as printed, to be what the TypeScript's command wrote and printed, and the bytes of `maintenance/reports/locator-coverage-2026-11-18.tsv` in the checkout;
3. the version 1 pattern to accept a row of a `value-check.tsv` file exactly when `check-values` did not report it as `locator_not_parsed`, over 14 files, with the recorded counts.

CI pins the counts as well: 52,278 locators read and reproduced, 2,432 value-check rows read and agreed. A thinner checkout fails.

The store cannot test what it has no example of. It holds no character beyond U+FFFF, no letter that folds onto an ASCII one and no line separator. `tests/fixtures/locator.json` is the TypeScript's answer on 2,336 locators written for that: 114 by hand, the 39 of the data repository's own sample, and the rest put together from parts by a seeded generator, about one part in five with an awkward character dropped in. 101 hold a character beyond U+FFFF and 65 hold half of one. It also records `selectorRole` on 32 keys, `carriesNoAddress` on 29 words, `renderLocator` on 23 sets of typed fields, `verdictOf` on 572 parses built by hand, `tallyLocators` on 5 lists and 19 runs of the command. Fifteen of the locators written by hand stand at the edges of the patterns that class a table: `Table Ix, col 1` is not a Roman numeral and `Table 2. Results, row 2` is not a dotted number. Three of the runs are of 23, 41 and 51 fully addressed locators in 80, where multiplying by 100 before dividing writes 28.8, 51.3 and 63.8 and dividing first would write 28.7, 51.2 and 63.7.

## Measured result

- Gate: 52,278 of 52,278 stored locators are read as the TypeScript reads them, byte for byte. The report is the committed one, byte for byte: 40,464 fully addressed, 3,212 partially, 8,192 with residue, 410 unanchored. The version 1 pattern agrees with `check-values` on 2,432 of 2,432 rows, 1,881 parsed and 551 not.
- Fixture: all 2,336 recorded locators agree, in the parse, the class, the coverage, the rendering, the segments and the version 1 answer, with the members of each parse in the order JavaScript writes them. Of 230 recorded matches of 77 patterns, 225 agree and 5 are refused for the reason above, and all 39 `toFixed` results agree.
- The command prints and writes what the TypeScript's prints and writes on the 11 recorded runs that succeed, exits 1 on the 3 that stop the TypeScript and 2 on the 4 it answers with its usage.
- Seeded faults: seven one-line changes to the grammar were each run against the tests and the gate. The tests fail on all seven. The gate fails on four (41 tokens to a segment in place of 40, a tie going to the later token, curly quotation marks not opening a quote, a line address not standing for a row) and passes three that the store has no example of (a closing bracket taking the depth below zero, Python's `lower`, Python's `strip`), which is what the fixture is for.
- Seeded faults after review: ten more one-line changes, each run against the tests, which fail on all ten. `\b` dropped from the Roman numeral pattern; the digit dropped from the dotted pattern; the share divided before it is multiplied by 100; the result files, the value-check files and the committed reports each sorted by code point in place of UTF-16 unit; the value-check files sorted by batch name in place of path; `?` allowed on something that can match nothing; `replace` stepping as `re.sub` does; and a `u` pattern that can match nothing run on a character beyond U+FFFF. Before the review's fixes the first six passed the tests.
- A differential run of `jsregex` against Node on 50,000 generated patterns it accepts, over 714,938 pairs of pattern and text, found no difference in what `exec` returns or `replace` writes. It is `scripts/fixtures/compare_patterns.py` with seeds 1 and 7 and `compare_patterns.mjs`, made on Node 26.7.0 on a laptop and not in CI, and it leaves out the `u` flag on text beyond U+FFFF. It is a way of looking and not a gate. An earlier form of it, run on the code before the review's fixes, found 1,711 differences in 85,854 pairs.
- Coverage: 100% of lines and branches of `src/rewire_evidence`, 5,880 statements and 2,150 branches, with no line excluded.
- Cost: the gate takes about 30 seconds.

Properties checked with Hypothesis:

- a match is a piece of the text at the place it names, replacing it with itself changes nothing, and replacing it with nothing removes exactly it;
- replacing every match writes first where the first match is, at most once for each place in the text and once at its end, and what it leaves does not depend on what is written;
- pairing units into characters undoes splitting characters into units;
- any text is read into fields whose verdict is the one `verdict_of` gives them, with no empty or untrimmed segment or residue, and reading it twice gives the same parse;
- text with no comma or semicolon is one segment;
- an ordinal after a row or column key does not change what the key names;
- a share in the report is the tenth nearest to the exact value of the double it is computed as, and the larger of two equally near;
- `fixed` is the exact value of the double rounded half up, by an independent calculation in decimal.

## Where the port differs, on purpose

- **`locator coverage --out` with no path is a usage error.** The TypeScript reads the missing path as no `--out` at all and writes the dated report.
- **A store that cannot be read is refused in one line, before anything is printed.** The TypeScript leaves with a stack trace and the same status, 1. A report that cannot be written is refused the same way, where the TypeScript has printed the table by then.
- **A result file that is not UTF-8 is refused.** Node reads the bytes it cannot decode as U+FFFD and goes on.
- **The stop on an empty match is not ported.** `consume` breaks when the leftmost match is empty. No token can match nothing, which a test holds, so the stop is never reached.
- **Three fallbacks of the TypeScript are kept and cannot be reached**, and because each is an expression inside a line, the coverage figure does not show that: `?? ""` for an address with no value group, `?? ""` for a selector with no key group, and `null` for a selector with no value group. Every address token has its value group outside any option, and every selector token its key and value groups, so a match always sets them. A selector with no value is reached by `render_locator` on an authored locator, which is recorded.
- **`render_locator` takes addresses as a list.** The TypeScript takes either `addresses` or an `address` and its `refines`, and `authored_addresses` makes the list from the second form.

## Known gaps

- **The zod schemas are not ported**: `spanSchema`, `locatorSchema`, `parsedLocatorSchema` and the four schemas of their parts. No record holds a span, and nothing in the store is checked against them. They belong with P11, which resolves spans.
- **Only the patterns the grammar uses can be run.** `jsregex` refuses the rest by name. A later stage that needs another construct has to add it and record cases for it.
- **A new pattern needs a recording before it runs.** Its sets have to be listed and recorded in CI, because the recording follows Node's Unicode version and no machine here is trusted to have the same one. A test fails while the list is stale.
- **The recorded lines are 2.6 MB in the repository**, and a pin bump replaces them.
- **The gates are still not required by the repository.** `main` has no branch protection and no ruleset, so a pull request can be merged while `checks`, `writes` or `fixtures` is red or still running. Requiring the three is a repository setting, which this workstream does not change. The oracle needs two of them green together: `fixtures` shows the committed lines are what the TypeScript writes, and `checks` shows the Python reproduces those lines.
- **V8 is not the specification where the `u` flag meets a character beyond U+FFFF.** The one difference recorded from Node 24.22.3 is refused, as described above. Node 26.7.0 was seen to differ in two more ways that 24.22.3 does not: `/[^x]$/u` and `/[\p{L}]$/u` find nothing in text that is one such character. A bump of the Node version has to record the cases again, and `scripts/fixtures/pattern_cases.json` holds all three.
- **The value-check files are sorted by path, as the recorder sorts them.** The order shows only in the list of rows that disagree, which is empty at the pinned commit.

## What a pin bump now takes

The Node that records is named by its exact version in `checks.yml`, 24.22.3 for the `fixtures` job and 22.23.5 for the `checks` job, and each action by a commit. The recordings name the version they were made with and a test requires the two to be the same, so moving to another Node is a commit that changes the workflow and every recorded file together.

Bumping `STORE_REF` changes the stored locators. The `fixtures` job then fails, and its `schema-fixtures` artifact holds the new `store-locators.json` and `store-locators.jsonl.gz` to commit. `STORE_LOCATORS` and `VALUE_CHECK_ROWS` in `checks.yml` are pinned by hand.

## Found in the TypeScript, not changed

`rewire-benchmark-data` was read and not touched.

- **No stored locator is read as an XML cell, and almost no text can be.** `qual_layer` stands before `addr_xml` in the token list and matches at `XML` wherever `addr_xml` would, so it wins the tie. 806 stored locators say `XML row 6 column 4` or the like, and each has the row and column inside the text of a `layer` qualifier, with no `xml_cell` address. The one way through is a letter directly before `XML` that is a word character under the `i` and `u` flags together and not under `i` alone, which is U+017F or U+212A: `qual_layer` has both flags, so its `\b` fails there, and `addr_xml` has `i` alone. The fixture records it.
- **No stored locator is read as a `layer_line` qualifier**, for the same reason and with the same exception: `qual_layer` takes `text-layer line 12` whole. 1,499 stored locators say `text-layer line`.
- **103 stored locators have a segment the grammar stops reading at 40 tokens.** With the limit at 41 they parse differently.
- **A quote opened by a curly mark is closed only by a straight one.** `splitSegments` holds the open quote as `'` whichever mark opened it, so in `row 'a, b', column 'c'` written with curly marks the rest of the locator is one segment.
- **`--out` with nothing after it writes the dated report** and says nothing about the missing path.
- **`parse` with a first argument that is empty prints the usage**, whatever follows it.
